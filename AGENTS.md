# tplay

Desktop audio player. Rust, eframe/egui GUI, rodio playback. Single window. LAN-only network access: a built-in SMB browser (no mount) plus a Volumes list of local block partitions — no internet services, connects only to user-specified hosts. 39 source files + `themes/` data folder; read all of them before changing anything — there is nothing else to explore.

## Rules

- Never screenshot or try to see the GUI. Use instrumentation (debug prints, egui memory, config files) or ask the user for feedback instead.
- Never add hardcoded constants. Use the config and theme files (`~/.config/tplay/*`, `themes/<id>/theme.json` layout/palette tokens).
- Comments must be clear and concise, and only added when needed. Say *why*, not *what* — the code already says what. Skip a comment that restates the line below it.
- Run `cargo fmt` before every commit.
- Commit messages must not be signed (no GPG/SSH signature trailer).

## Layout

- `src/main.rs` — bootstrap **and the shell**: window options (680x460 default, resizable, min 320x160, no native title bar), then `struct TPlay { app: TPlayApp, themes: ThemeState, prev_frame_time: Option<f64> }`, which is the `eframe::App`. **`raw_input_hook` is the load-bearing part of that struct beyond the two UI fields**: eframe 0.36 fills in `RawInput::time` and then hands the rest to the app **without ever setting `predicted_dt`**, which therefore stays at `RawInput`'s `1.0 / 60.0` default for every frame — so the shell measures the real interval and writes it, or nothing (see **Visualizer** → *`ATTACK_MS`* for why that is 2x wrong at 120 Hz and 4x at 240 Hz, and what it feeds). The pure policy is `app::frame_dt_from`, which is in `app.rs` rather than here only so a test can reach it. It owns the two things that are genuinely UI — the `ThemeState` (a switch re-decodes icon textures, which needs a `Context`) and the frame order — and drives one frame as *draw, then advance/drain/persist, then repaint if in flight*. `config::load()` happens here too, because `TPlayApp::new(&Config, library_db::TrackDb, Mixer)` takes the loaded config, the loaded database and a `rodio` `Mixer` — the app holds **no audio device**, only the `Arc`-backed mixer every `Player` attaches to, so a test can build the same struct. The database is a parameter rather than something `new` loads itself because a database carries **its own** file path, and a test's `TPlayApp` must physically be unable to reach the developer's real `library.json`. `TPlay` also opens the device (the `BufferSize::Fixed` + fallback arms live here) and keeps it in `_output`, which is load-bearing despite the underscore: dropping the `MixerDeviceSink` stops the cpal callback, and nothing else pulls the mixer. **This is what makes `app.rs` egui-free**: `TPlayApp` holds no `Context` and owns no theme, so it cannot implement `eframe::App` and does not try.
- `src/app.rs` — `TPlayApp`: ALL app state + logic, **zero UI code and zero egui dependency** (it imports no `egui`, no `eframe` and no `gui::` — grep it). Owns the `Player` and the `Mixer` it attaches to — the *device* is the shell's (see above). `TPlayApp::update(now, closing, theme_id) -> bool` is the per-frame tick: advance, drain, persist, apply network events, and report whether a repaint is wanted. The three places that used to call `ctx.request_repaint()` return a `bool` instead, because the app has no `Context` to call it on. **No docking state, no theme** — those live in the GUI layer / the shell. Four things deliberately do *not* live here despite being app state: the settings file's on-disk shape and the six playback settings (`src/config.rs`), the EQ gains/presets (`audio::eq::EqSettings`), the Library's browse state (`library::LibraryState`), the gapless/crossfade pre-buffer decision (`audio/transition.rs`).
  - The app **owns** those groups and exposes each as one accessor pair — `prefs()`/`prefs_mut()`, `library()`/`library_mut()`, `eq()`/`eq_mut()`, plus the long-standing `network()`/`network_mut()`. That is the whole GUI↔app boundary: a pane depends on `EqSettings`, not on method names this file invented for it. The **theme is not one of them** — it is not app state at all (see the shell above), so the GUI receives it as a `&ThemeState` threaded down from `main.rs`, and the app only ever handles its `id`, as a `&str` argument to `flush_config`.
  - **The rule that decides what stays on `TPlayApp`:** a method survives only if it touches state *only the app has*, or performs an effect that *spans* owners — persist, re-list, scan, rebuild the sink, drain the network. Anything that was a bare forward to one owner (a getter per value, a setter per setting) is gone. That's why `set_library_sort` remains (it needs `&tag_cache` and `app.library_mut()` — two borrows of `app`, one mut one shared, won't compile), why `set_show_hidden` re-lists, and why `toggle_shuffle`/`toggle_repeat` are still methods: they flip private app fields, and a field mutator isn't a forward.
- `src/config.rs` — `~/.config/tplay/config.json` and nothing else: `Config`/`EqData`/`LibraryData`/`VizView`, their serde defaults, `load()`/`save()`, **and the live `Prefs**. The file half is one-way — `TPlayApp::snapshot` builds a `Config` from its own state and `flush_config` hands it over; this module has no idea what a theme or a shuffle *does*. The fields are `pub` because they document the format `config_persistence.rs` pins, not because anything reads them back through here. Re-exported from `app` (`pub use crate::config::{…}`) since the GUI and the tests already reach those types through `app`.
  - **`viz_view` takes a custom deserializer, and it is not optional politeness.** A derived `Deserialize` fails the *whole* `Config` on an unknown enum variant, and `load_from`'s only answer to a parse error is to copy the file aside and return `Config::default()` — so one unrecognised value cost the user their volume, EQ gains, saved SMB servers and favourites. Reachable two ways: a `config.json` written by a build with one more view (the downgrade case), and a typo in a file this doc calls hand-editable. `de_viz_view` reads the name and falls back to the default, via `serde_json::from_value` — serde has already decoded the string, so the text still needs quoting before the variant name is matched. The *written* form is unchanged (a bare string), so this cannot move the on-disk format. Pinned by `an_unknown_viz_view_costs_the_other_settings_nothing`, whose claim is two-part: the unknown value falls back **and the rest of the file survives** — a fix that only stopped the panic would still have lost the file. This is the answer `library_db::Rule` already gives for the same hazard, and the two disagreed.
  - **The same function shipped a second, quieter bug: it accepted only the Rust variant name, and one of the views is spelled for people.** `VizView::name()` is what the picker shows, and it says "VU meter" where the derived `Serialize` writes "Vu". A hand-edited `config.json` naming a view the way the UI spells it therefore read as *unrecognised* and fell back to the default — the exact loss this function exists to prevent, arriving through the door it was built to guard. It was invisible because nothing looked a view up by name: the visualizer dispatched on an exhaustive `match` over the enum, so the two spellings were never compared. Converting the views made the dispatch a table lookup keyed on `name()`, and the same disagreement became a view that renders nothing. Both spellings are now accepted, `Serialize` is untouched so the on-disk format does not move, and `every_view_name_round_trips_through_the_config` pins it in both directions. **That disagreement is why the config records `Chladni3D` and the dropdown said `Chladni 3D`, and it is the second of the two to have the same root cause** — a UI label and a storage spelling that nothing reconciled.
  - **`Prefs`** — the six user-tunable playback settings (viz view, remaining, gapless, crossfade + duration, balance) as one owned group, the live counterpart of the matching `Config` fields. `TPlayApp` had **twelve** near-identical setters for these, each clamping independently; the clamping now lives in `Prefs` and nothing else. `Prefs` setters **only clamp** — they used to also report whether anything changed, purely so a caller could skip raising a dirty flag, and the content compare below made that flag unnecessary. `balance` is an `Arc<RwLock<f32>>` (not a plain `f32`) because `BalanceSource` reads it per audio frame — `Prefs::balance_shared()` hands the audio source its handle. `from_config` clamps on load, so a hand-edited `crossfade_secs: 900` cannot reach the fade math.
  - **`should_flush(changed, now, last_save, closing) -> bool`** + `CONFIG_SAVE_DEBOUNCE_SECS` (0.5) — the write throttle, pure and time-injected so it is testable without an eframe `Context`. `changed` is the caller's content comparison, not a hand-set flag. See **Appwide settings** for why it exists.
  - **`Persisted`** — the *state* that throttle reads, not the policy: the content last written and when. `new(seed)` (so a clean start writes nothing), `due(now, closing)` (**whether it is worth serializing at all** — the debounce asked *before* the compare, because the point of the debounce is to skip the work, and a `library.json` is the whole tag cache), `wants_write(content, now, closing)` (the policy over one file's content), and `note_written(content, now)` (called *before* the write, so a failed write is not retried every frame). It exists as one type because **two** files now keep that pair — `config.json` and `library.json` — and a third (`dock_layout.json`, in the GUI layer) keeps the same idea in egui memory; the policy stays pure and shared so neither caller can half-apply it. See **Appwide settings** for the `flush_config` / `flush_db` pair that uses it.
  - **One definition of "default", and it is `Config`'s `Default` impl.** A *missing* file falls back to `Config::default()`; a file with fields *absent* deserializes through the `#[serde(default = …)]` attributes. Derived, those two disagreed and a fresh install got `volume: 0.0` — a silent player — where an install with `{}` got 1.0. Every field now carries `#[serde(default)]` (a hand-edited file with one key omitted used to be unrecoverable) and `Default` is written out to call the same `default_*` fns. Pinned by `a_missing_config_agrees_with_one_whose_fields_are_absent`, which serializes both and compares.
  - **A malformed file is copied aside, not silently replaced.** `TPlayApp::new` seeds its write baseline from what `load()` returned, so returning defaults means the first `flush_config` overwrites the user's settings — a single typo cost everything. `load()` writes the original to `config.json.broken` and says so on stderr. A *missing* file is a fresh install, not damage, and leaves nothing behind. `load_from(Option<&Path>)` is the injectable form, so the case is testable without touching the real config.
  - **`save` is write-then-rename** (`config.json.part` → `config.json`), and that is what keeps the bullet above from being self-inflicted. A plain `fs::write` truncates in place, so a process killed mid-write leaves a truncated file that reads back as *malformed* — and the recovery for a malformed file resets every setting to its default. The `.broken` copy rescues a file that was *already* damaged; the atomic write is what stops this write from being the one that damages it. `network::run_spool` uses the same shape, where the consequence is worse: a partial spool file passes `is_ready`, so it plays as a track carrying the wrong tags and the wrong duration.
- `src/lib.rs` — public re-exports for testing (`app`, `audio`, `config`, `gui`, `library`, `library_db`, `network`, `playlist`, `tracks`), plus a `pub use rodio;` so a test can build the `Mixer` that `TPlayApp::new` takes without a dev-dependency that could drift from the real one.
- `src/gui/mod.rs` — declares `coordinator` + `dialogs` + `panes` + `theme`.
- `src/gui/dialogs.rs` — the app's only three dialogs, all in-app `egui::Modal`s: the Yes/No `ConfirmAction`, the shared save-name prompt (`SaveTarget`), and the **track editor** (`ask_edit` — a 5-star row plus the four text tags). A call site arms one (`ask` / `ask_save_name` / `ask_edit`) and the coordinator calls `dialogs::show` at the end of the frame, above the dock area. State lives in egui memory under `CONFIRM_ID` / `SAVE_NAME_ID` / `EDIT_ID`, so `TPlayApp` stays UI-state-free; actions are enums, never closures (a closure cannot be stored in egui memory).
  - **The editor is one dialog, not a rating picker plus a tag form.** A separate text editor would have been a fourth shape with its own arm, its own memory key and its own error path, for a form over the track the stars already edit. **Two write triggers, two answers:** a star click writes immediately — it is a complete, reversible action, and "the same star again clears" only works if the click lands at once — while the text fields write on **Save**, so the modal closes on a success and stays open with the error on a failure. A rating is deliberately *not* re-sent with the text (the stars already wrote it); a second write of the same value is a second chance to fail. There is no Cancel button: a backdrop click dismisses, as it does the confirm.
- `src/gui/coordinator.rs` — `update_ui(app, themes, ctx, ui)`: applies the theme's egui visuals, then draws one frame's `DockArea` (egui_dock). **The fourth argument is new and is not optional:** egui 0.36 draws a frame as a `Ui` and every panel is shown *inside* one, so the top bar is `Panel::top(..).show(ui, ..)` and the dock area is `DockArea::show_inside(ui, ..)` inside a `CentralPanel`. `ctx` is that `Ui`'s context, cloned at the call site in `main.rs`, so nothing below it needs the indirection. `themes` is `&mut ThemeState`, owned by `main.rs`'s shell, so the ☰ menu can re-decode icons and the panes can read tokens without the app holding either. Implements `TabViewer` for `Pane` enum; calls the six pane functions in `ui()`. Loads dock layout from egui memory + `~/.config/tplay/dock_layout.json`; saves to disk only when the layout changes or the app closes. The ☰ menu re-adds closed panes. Draws `dialogs::show` **after** the dock area, so any dialog armed mid-frame (by a pane or the menu) paints on top and runs there.
- `src/gui/theme.rs` — data-driven theme system. `Themes::load()` scans `~/.config/tplay/themes/` (user, wins on id clash), `<exe_dir>/themes/` (shipped with the app), `./themes/` (dev: `cargo run` from repo root) and merges by theme id. Each `themes/<id>/theme.json` carries `id`, `name`, `base` (dark/light), `metadata_font` (monospace/…), and the 13-token `Palette` (`--bg`, `--accent`, `--row-even`, …) as hex strings; invalid files are skipped with an eprintln, and a hardcoded dark fallback theme guarantees a non-empty list (broken install). `apply(ctx, &Theme)` maps tokens onto egui `Visuals` each frame so a mid-session switch lands instantly. Selection persists to `~/.config/tplay/config.json` (the `theme` field); missing config = `dark`.
- `themes/<id>/icons/*.svg` — per-theme icon set; resolution order, the 23 names and the rasterization conventions are under **Themes** below. `theme::load_icons` renders them through resvg synchronously into egui textures at startup and on skin switch (NO egui async loader — the URI loader path showed pending/error placeholders and stretched buttons).
- `themes/recolor_icons.py` — **recolours the icon set from the palettes, and does nothing else.** `python3 themes/recolor_icons.py [themes…]`, plus `--list` (the token each slot is baked in) and `--check` (report drift, write nothing). It only rewrites `fill`/`stroke` **hex values, in file order** — never path data, `viewBox` or structure, and never a `fill="none"`, which is structural: the hand-authored icons group their stroked paths under `<g fill="none" …>` and painting that turns a line drawing into a blob. So it cannot alter a glyph's shape, needs nothing installed, and cannot clobber the seven icons original to this repo. Two rules make it work: colours are applied **positionally** rather than matched against the current hex, because a token edited in `theme.json` no longer matches anything and matching on it would leave that theme's icons stale forever; and a single-token slot paints every attribute the same colour, because the hand-authored icons are several stroked and filled paths of one ink. `nocover` is the only multi-colour file (panel_bg plate, border edge, secondary disc) and its three tokens are positional. **`logo` is the one slot it skips entirely**, via a `FIXED` set: it is full-colour brand artwork with no palette token behind it, so a `TOKENS` row would be a lie. A slot with no row is already left alone, which means `FIXED` is not protecting the bytes — without it the logo is reported as a problem on every run and `--check` exits 1 forever, a CI failure for a file that is correct. `--check` is the safety net for the workflow the deleted `generate_icons.py --check` used to provide; the "mark with no slot" direction is now a test (see `gui_tests.rs`).
- `src/gui/panes/{now_playing,playlist,equalizer,visualizer,album_cover}.rs` — one free function per pane, each taking `(app: &mut TPlayApp, themes: &ThemeState, ui: &mut egui::Ui)`. `themes` is a shared borrow, so a pane can read the palette and look up icons while holding `&mut app` — the reason it is a parameter and not a field on the app. Position-independent — work identically docked anywhere. Their shared module root `src/gui/panes/mod.rs` declares the six and holds `row_visible(ui, row_h)` — the one-row visibility gate both scrollable lists (the Library and the Playlist) call, in one place precisely so a fix to one list cannot skip the other (see **Neither list virtualises**).
- `src/gui/panes/library/` — the one pane too big for a single file, split by its three visible parts (same shape as `panes/visualizer.rs` + `panes/visualizer/views/`). `mod.rs` is the module root and holds only `library_pane`, which orchestrates and nothing else: clone the theme, read the browse state and the `NET_FORM` input, draw the header, then the sidebar and the main column side by side. `header.rs` = the breadcrumb, `sidebar.rs` = the Places/Volumes/Network/Favorites column, `listing.rs` = search + sortable header + rows + counts + Add All + the remote browser. `dir_name`, `LIB_INIT` and `NET_FORM` live in `mod.rs` because the orchestrator is their only shared user — a private item there is already visible to all three children.
- `src/library.rs` — pure logic: directory listing, tag/duration/**star-rating** reading via `lofty` (a rating is a Popularimeter *in the file*, not app state — see **Library**), background scan thread (`scan_files` + mpsc), `TrackInfo` cache, sorting (`sort_key` with DEL prefix for empty values), **playlist file formats** (`PLAYLIST_EXTENSIONS` — `.tplay`/`.m3u`/`.m3u8`/`.pls`; one read and one write dispatcher, see **One playlist file format**), **local volume discovery** (`Volume::parse_mounts`/`parse_mounts_with_labels`/`mounted_volumes` from `/proc/self/mounts` + `/dev/disk/by-label/` — pretty filesystem labels win over UUID mountpoint names; `PSEUDO_FSTYPES` + `BOOT_MOUNTPOINTS` (`/efi`, `/boot`, `/boot/efi`) excluded).
- `src/library_db.rs` — the persistent library database, `~/.config/tplay/library.json`. `TrackDb` owns **two maps with no shared insert path** — `tags` (the tag cache, reached through `cache()`/`cache_mut()`) and `stats` (`HashMap<PathBuf, PlayStats>` — plays, last played, first seen); the full rationale is under **Non-obvious machinery** → *Two maps, no shared insert path*. Plus `note_played`/`stats_of`/`PlayStats::describe` (the row tooltip's wording), `snapshot` (the borrowed serialize side `DbFileRef`, the content the write throttle compares), `at`/`load`/`load_from` (a database carries **its own** file path, and `new` has none — so a test's `TPlayApp` physically cannot reach the developer's real library), `persist` (stamp first seen, then `config::atomic_write`), and malformed → `library.json.broken`, exactly as `config::load_from` does. **Smart Views** are `Rule` + `SmartView` + `presets()` + `TrackDb::{views, add_view, remove_view, select}` — see **Library** → *Smart Views*. `snapshot` borrows (`DbFileRef`) because the two directions are not symmetric: `DbFile` owns its keys because deserializing into a long-lived `TrackDb` needs that, and serializing needs only a walk — the owned form meant deep-cloning every `PathBuf` and `TrackInfo` to discover nothing had changed. `equal_databases_serialize_identically` pins the mechanism the throttle rests on: equal content must serialize equal, or the file is rewritten forever and the symptom is a file that looks fine plus a compare that is never equal, which no behavioural test can see.
- `src/network.rs` — built-in SMB browsing client (pure Rust via `smb2`, no system mount): `smb://host/share/rel/path` URI model (`is_remote`/`split_uri`/`share_uri`/`dir_uri`/`child_uri`), a spool cache (`spool_key` FNV-1a 64 + `cache_path` under `<cache>/tplay/smb/` — extension kept from the URI so rodio can sniff it), `SmbCmd`/`SmbReply` channels, the smb2 ops (`run_list_shares`/`run_list_dir`/`run_spool`), and the `Network` state object owning ALL network state (servers, session passwords, browse position, pending spool, worker channels) with the browse/spool/drain API. Playback is **spool-then-play**: download the whole file to the cache before decoding, so the rodio pipeline never touches the network.
- `src/tracks.rs` — **the source-agnostic track surface** (see **Tracks: one surface per source** below). The single place that knows a track can be local or remote, and the only module that touches the filesystem for a track: readers that take a track id and return the *thing* asked for (`open`/`info`/`probe`/`cover`) plus `is_ready` (the pre-buffer predicate), **`write_tags`** (the one *writer*), `normalize` (playlist entry → the id everything stores), `split_for_tags` (batch → the two tag transports, **skipping what the cache already has**), and `TagReader` (owns the local scan receiver and applies remote tag results). The cache test lives inside `split_for_tags` rather than in the caller, and that is the point: the share browser asks for every uncached row *every frame*, so filtering into a `missing` vector first meant a `PathBuf` clone per row per frame before the split even began. One pass, and a remote row costs the one `String` the worker command needs. The local half still clones — it moves into a spawned thread and must be `'static` — which is the floor without changing `scan_files` to take references, which would only move the clone.
- `src/playlist.rs` — **the playlist's content operations, and nothing else** (egui-free, no state): `sort_tracks` (delegates to `library::sort_key` over the same `SORT_OPTIONS` columns, so the playlist and the file list order alike), `shuffle_tracks` (Fisher-Yates), `dedup` (one-pass, first occurrence wins — `Vec::dedup` is adjacent-only and the repeats that actually arrive come from a loaded file with other entries between them), and the XorShift64 RNG (`rand_u64`/`rand_usize`, moved out of `app.rs` because every draw it serves is a playlist shuffle). Three things are deliberately **not** here, and the split is the point: the **file formats** stay in `library.rs` (`playlist_text`/`read_playlist`/`is_playlist` over `PLAYLIST_EXTENSIONS`), the **state** stays on `TPlayApp` (the list itself plus `playlist_dirty`/`current_index`/`played`, and the `cancel_xf()` a reorder owes a live crossfade), and **shuffle navigation** stays in `app.rs` beside `played` (the peek/commit split is a load-bearing invariant documented there). Same shape as `transition::arm_plan` — the decision is pure and tested alone, the effects stay where the state is.
- `src/audio/mod.rs` — file-level helpers, no playback logic:
  - `probe_duration` — symphonia-based duration probe; fallback when rodio's `Decoder::total_duration()` is None (mainly MP3). This is why `symphonia` is a direct dep.
- `src/audio/eq.rs` — 10-band graphic EQ (`EqSource` wrapping `rodio::Source<Item=f32>`). RBJ peaking EQ coefficients (w3.org audio-eq-cookbook). Gains live in `Arc<RwLock<EqShared>>` shared with GUI; `EqSource::refresh()` read-locks every `REFRESH_EVERY` samples, UI write-locks — no sink rebuild, no audio restart. 0 dB = exact identity filter (A=1). **`EQ_BANDS`** is `EQ_FREQUENCIES.len()`, and every array sized by the band count is written `[f32; EQ_BANDS]` / `[Biquad; EQ_BANDS]` rather than `[f32; 10]` — so an eleventh band is a one-line change the compiler checks everywhere, not a four-file edit that compiles until a band reads out of bounds. Also owns `EQ_PRESETS` and `preset_for(gains)` — the presets sit beside `EQ_FREQUENCIES` because they are curves over those bands, and `preset_for` is pure, so the preset name is derived from the gains and never stored. **`EqSettings`** owns that `Arc` for the app: the clamp (`EQ_GAIN_MIN_DB`/`MAX_DB`), the preset apply, and the name derivation, handing `EqSource` a **cloned** handle via `shared()` because the source outlives any borrow. Its setters still return whether the value changed (the config compare no longer needs to know, but the answer is what its tests pin, and it costs nothing to keep).
- `tests/` — ALL tests live here; each file is its own auto-discovered test binary (cargo runs each once). `tests/common.rs` provides shared helpers (temp dirs, minimal WAV/FLAC generators, duration assertions, and `TestApp` — a `TPlayApp` with a software audio device, used by `playback_integration.rs`). `common::write_tagged_mp3` hand-builds a real ~125 KB MP3 with real ID3v2 tags (ID3v2.3 TIT2/TPE1/TALB + 300 silent MPEG-1 Layer III frames) — it exists because no encoder dependency is available and lofty ships no test assets, and it is the fixture the whole remote-tag path is verified against. Individual suites: `eq_tests.rs`, `playlist_tests.rs`, `library_tests.rs`, `gui_tests.rs`, plus the second-wave suites below. `playlist_tests.rs` also carries the **share-playlist** serialization rules: `smb_uris_are_not_joined_onto_the_base` (the `is_relative` trap — an `smb://` entry read with a share base must survive verbatim), `relative_entries_resolve_against_a_share_uri_base` (with a premise guard proving the cache-dir base is wrong), `mixed_playlist_roundtrips_through_json`, `default_playlist_name_keeps_the_tracked_stem` and `playlist_file_name_appends_the_extension_and_strips_separators`. `library_tests.rs` carries `read_info_gives_tags_and_a_true_duration_from_a_whole_file` (the remote path's load-bearing claim: a full read gives tags AND a duration matching the file's 300 frames, which no prefix could) and `sort_entries_orders_both_sources_the_same_way` (one sorter, and the Title column interleaving folders by their own name). `smb_helpers.rs` carries `select_evictions_never_removes_a_played_file` (must free enough AND never touch a played file, even when that means falling short), `evict_unplayed_in_deletes_what_it_selects` (the **wiring** over a real temp spool dir — a pure `select_evictions` cannot catch a key that does not resolve to a file) and `tag_attempts_are_bounded_and_cleared_on_success` (the retry cap, and that `busy()` ignores the attempt map so a retained failure cannot pin a permanent repaint).
- **Headless boundary: lifted.** `TPlayApp::new(&config, db, mixer)` needs no `CreationContext` and no audio *device* — only a `Mixer`, and `rodio::mixer::mixer` builds one with no hardware. `tests/playback_integration.rs` therefore constructs the real struct and drives real playback against a software device that runs faster than real time (see that suite's entry). What remains untestable needs a real window: the panes' layout (covered by mirroring in `gui_tests.rs`, and — since the playlist's chrome rows arrived — by `the_playlist_pane_leaves_its_list_the_height_it_was_given`, which runs the **real** `playlist_pane` in a headless `Context` and measures the geometry, so a mirror is no longer the only option for a pane) and the cpal callback itself. Pure playback logic (shuffle navigation, drag index math) is mirrored branch-for-branch as free functions in `tests/` — the same convention `playlist_tests.rs` and `drag_drop.rs` follow. **Prefer moving the logic out to mirroring it** (see `transition::arm_plan`, below): a mirror is a second copy that can drift from the first. ## Build / verify

- `cargo check` — compiles fast with cached target/.
- `cargo test` — runs all tests.
- `cargo fmt --check` and `cargo clippy --all-targets -- -D warnings` — what CI gates on, so run them before pushing.
- `[profile.release] opt-level` is deliberately absent — 3 is Cargo's default.
- **CI** (`.github/workflows/ci.yml`) — **a `v*` tag push is the only trigger**: one job on `ubuntu-latest` runs `fmt` → `clippy -D warnings` → `test`, then, **only because those passed**, a release build packaged as `tplay-linux-x86_64.tar.gz` (the binary + `themes/`, because `theme_dirs()` looks in `<exe_dir>/themes`) and attached to a GitHub release at that tag. The version is the tag you pushed, so nothing is bumped in `Cargo.toml` to release — but there is also **no CI on plain pushes or pull requests**, so nothing checks a commit before it is tagged. Two system packages: `libasound2-dev` (cpal/ALSA is a build dep) and **`mesa-vulkan-drivers`**, which exists for one test — `the_callback_paints_the_pane_and_nothing_outside_it` runs a real wGPU device, and lavapipe is a *software* Vulkan ICD, so the visualizer's callback is rendered and the pixels read back with no GPU present. Without it that test skips, which is exactly how a broken viewport or a shader that writes nothing reaches a release. Everything else (X11/xkbcommon/wayland) arrives via dlopen and the rest of the tests are headless, so there is no xvfb and no audio device.

## Playlist

- `playlist: Vec<PathBuf>` — ordered list of tracks; no duplicates (deduped on add **and** on load)
- `playlist_file: Option<PathBuf>` — the `.tplay` file this playlist was saved to / loaded from; `Some` → Save overwrites it, `None` → Save asks for a name
- `playlist_dirty: bool` — edited since the last save/load; set on add/remove/move, cleared on save/load/new. Drives whether New/Load ask a confirm.
- `current_index: Option<usize>` — index of currently playing track in playlist; `None` = not playing from playlist (direct open from Library)
- `shuffle: bool` — shuffle mode enabled
- `repeat: bool` — repeat mode enabled
- `played: Vec<usize>` — history of indices played in this shuffle cycle (for prev/next)
- `rng_state: u64` — XorShift64 state for shuffle (replaces `fastrand` dependency)
- **Add Files / track additions come from the Library** — the `+` row button and the **Add All** header button call `add_files` (dedup checks); the old Add Files dialog button in the pane footer is gone, and **play on an empty playlist is a no-op** (`TPlayApp::play` used to open an OS file picker there — the last native file dialog)
- **Header**: the pane shows the current playlist's name at the top — the tracked file's stem when saved/loaded, else "Untitled", via the single `app.playlist_name()` getter (no pane-side derivation; follows New/Save/Load live)
- Click track name to play; drag track name to reorder; ✕ icon button removes track (✕ and the right-aligned FORMAT column sit in a fixed 24px row; rows alternate `--row-even`/`--row-odd`, the active row gets a full-row `--accent` tint plus a 3px `--accent` left stripe; row content is inset 6px so the leading number clears the stripe; rows show the tagged **title** — filenames render without their extension until the tag scan lands — and a truncated `artist · album` secondary block, with FORMAT carrying the type)
- **Shuffle** — plays each track once in random order; clicking a track resets shuffle
- **Repeat** — loops playlist (sequential) or shuffle cycle
- Transport (play/prev/next/stop) uses the theme's icon textures; the shuffle/repeat mode toggles sit beside them (same icon set, lit via egui's selected visuals while active)
- **Play greys out when there is nothing to play** — `TPlayApp::can_play()` (a getter next to `has_prev_track`/`has_next_track`, mirroring `play()`'s branches) feeds `theme::icon_button`'s `enabled` flag, the same gate prev/next use. False when nothing is loaded *and* the playlist is empty, and while a remote track is spooling — that one starts by itself when it lands, and `play()` returns early for it, so the button would do nothing either way. Note the play/pause *icon* is chosen separately (`is_paused() || is_empty()`), so a greyed ▶ is the normal resting look of a fresh launch, not an error.
- Auto-advance (`advance`) fires on natural track end (sink empty, unpaused, `current_path` set), called from `TPlayApp::update()` every frame. The `current_path.is_none()` guard is what stops a failed load from cascading through the whole list one entry per frame.
- **Remote tracks** (`smb://` URIs in the playlist): there is no separate code path. Every play goes through the one `play_now` entry point, which asks `tracks::is_ready` — a cached track plays via `start_track(track)` (tags keyed by the id); a miss tears down the sink, clears `current_path`/`total_duration`, and asks the worker to spool it (`Network::spool` also marks it pending, and marks the track played). `Network::drain` returns the `Spooled` event when the download lands for the still-pending track (a stale reply for a superseded track is dropped) and `update()` promotes it into the sink, so Now Playing shows "Loading from server…" while `network().pending()` is set, and `advance()`'s `current_path.is_none()` guard can't cascade past the pending track. **Gapless/crossfade apply to any track whose bytes are on hand** (the xf arm asks `tracks::is_ready`, not `is_remote`), so an already-spooled network track crossfades like a local one; `stop()` calls `discard_pending()`. The builder is `Option`-returning and runs *before* any state flips, so an unreadable incoming file skips the arm and costs a gap — never the process. A re-requested track hits the disk cache instantly. The cache is bounded only by `Config::spool_cache_mb` (see **Spool cache eviction**).
- **Save Playlist** — first save asks for a filename in an in-app modal (in the Library's current folder, suggested `playlist.tplay`) and writes the current playlist in the format that filename names (see **One playlist file format**; paths only — shuffle/repeat are appwide, never playlist content). The pane remembers the file (`playlist_file`), so later saves overwrite it directly — no dialog. Loading a playlist from the Library also sets the tracked file (save writes back to the source) and **stops playback** (same as **Create Playlist** — the swap is silent); **Create Playlist** clears the tracked file so a fresh playlist asks where to go. Button hover shows the overwrite target ("Overwrite playlist: …"). A **failed** write no longer marks the playlist clean or tracks the file — that was a bug: both were set unconditionally, so a failed save claimed success and every later save overwrote a file that was never written.
- **One playlist file format layer** (`library.rs`) — `.tplay` (ours), `.m3u`/`.m3u8` and `.pls` (what other players speak), dispatched off the extension in both directions:
  - **`PLAYLIST_EXTENSIONS`** is the one list, and `is_playlist` matches it. That single widening is what makes interchange files appear in the Library and the share browser as "Playlist" rows — every other `is_playlist` call site already meant "a playlist file, not audio" (the tag scan, Add All, the 4-column header, `library_scanning`), which is exactly what an `.m3u` is. **No GUI file changed for interop.**
  - **Read**: `read_playlist(path, base)` picks the parser from the extension, and *all three* hand their entries to the same private `resolve_entry`. That sharing is load-bearing, not tidiness: `.m3u` files are relative-path-heavy, and the `smb://` trap (a URI is `is_relative`) would have to be avoided three times over otherwise. `parse_m3u` drops blank and `#` lines (`#EXTM3U`, `#EXTINF:…`, the `#EXT-X-*` set) and turns `\` into `/`; `parse_pls` sorts `File<n>=` entries **numerically** (`File10` follows `File2`) and deliberately ignores `NumberOfEntries`, which real files lie about. An unknown extension falls through to `.tplay` JSON, so a malformed file still returns `None`.
  - **Write**: `playlist_text(path, tracks)` is the single serializer, called by `write_playlist` *and* by the SMB save arm — so the local write and the bytes shipped to the worker cannot disagree about the format. (An `smb://` target's extension is its URI's, so a share save follows the same rule.) It replaced `playlist_json`, which took no path and so could only ever write one format.
  - **Export has no UI**: `playlist_file_name` already normalized the typed name, and keying it off `is_playlist` means typing `mix.m3u` in the existing save-name prompt keeps that extension and writes m3u. A dedicated "Export…" button is the thing to add if nobody finds it.
  - **Entries go out verbatim** (absolute, or the full `smb://` URI) — what other players reliably read, and the alternative (rewriting relative to the playlist's own directory) is the very transform that hosts the `is_remote` trap.
  - Tests: `playlist_tests.rs` carries the format half — m3u metadata/backslash/relative handling, pls index order vs a lying count, an `smb://` entry in an m3u, and `a_written_playlist_reads_back_in_every_format` (what we write, we read: the check that a `.m3u` holding JSON fails), plus `recognized_extensions_split_audio_from_playlist` for both sets.
- **Playlists on SMB shares** (load *and* save, no mount):
  - **Load.** A playlist file on a share (`.tplay`, `.m3u`, `.pls`) gets a row in the remote browser (see the shared file list below). Clicking it confirms first when the playlist is dirty — the same gate as a local playlist click — then `Network::fetch` spools the file. That uses `SmbCmd::Spool` but a **second slot** (`fetch_req`, separate from the playback `pending`) so reading a playlist can never displace a track that is still spooling, or vice versa; `drain` returns `Event::Fetched` and `update()` applies it via `load_fetched_playlist`. Stale replies drop against the slot.
  - **`read_playlist(path, base)` takes an explicit base, not `path.parent()`.** A remote playlist is read from its **spool cache copy**, so resolving against that file's own parent would silently drop every relative track. Local callers pass the file's directory; remote callers pass `network::uri_parent(&uri)` — the share directory the playlist was browsed at. This is why an `.m3u` off a share works for free: it takes the same `base`.
  - **`smb://` entries are never joined onto the base.** They only *look* relative: `Path::is_relative` is true for anything without a leading `/`, so keying off it turns `smb://nas/m/x.mp3` into `smb://nas/m/smb://nas/m/x.mp3`. Hence two *positive* `is_*` tests in the shared `resolve_entry` — `is_remote` and `is_absolute`, which are disjoint, since a URI is never absolute. Guarded by `smb_uris_are_not_joined_onto_the_base` + `smb_uris_survive_an_m3u_import_onto_a_share_base` (`playlist_tests.rs`) and the URI half of `smb_helpers.rs`.
  - **Save.** `save_playlist_to` branches on `is_remote` → `Network::save` → `SmbCmd::Save` → `run_save` (`client.write_file_pipelined`, one compound CREATE+WRITE+FLUSH+CLOSE with `FileOverwriteIf`, so no file lifecycle to manage). The write is async, so `playlist_file`/`playlist_dirty` are only updated when `Event::Saved` confirms — dispatching is not success. On success the app also calls `refresh_network_dir` so the new file appears in the listing without navigating away and back. Entries are written as **full `smb://` URIs** (no relative rewriting), so a share playlist is portable only in the sense that it always resolves here.
  - **Where Save writes** (there is no native dialog, so the target is a rule): `playlist_file` is already a remote URI → overwrite in place, no UI; otherwise a name is asked for in the one in-app modal (`gui/dialogs.rs`) and written into the directory on screen — a share directory if the Library's remote browser has one open, else the Library's current folder. The suggested name is `library::default_playlist_name` (the tracked file's stem) and typed input goes through `library::playlist_file_name` (appends `.tplay` unless the typed name already carries a playlist extension — which is how Save doubles as an export — and strips path separators rather than sending a bogus server path; blank cancels). `dialogs::SaveTarget` holds that choice (`PlaylistShare` / `PlaylistLocal` / `Layout`); the directory is captured at press time, so navigating afterwards cannot retarget an open prompt. **A save cannot browse for a directory** — navigate the Library first if you want another folder, exactly as the share branch already required.
  - A remote `last_playlist` restores through the same async `fetch`, because `Path::exists()` is always false for an `smb://` path and would skip the restore silently. It fails until the user logs in again — passwords are session-memory only, so there is nothing to reuse.
- **New Playlist** — clears the current playlist (replaced the old Load button); the toolbar's `Icon::NewList` button is it, with a tooltip because an icon carries no label. Loading now happens in the Library by clicking a `.tplay` file. New and Load ask first (the in-app confirm modal) only when the playlist has unsaved edits (`playlist_dirty`) — a clean switch is silent, and the check lives at the call site, which acts directly instead of arming. The ✕ per-row remove always asks.
- **Removing a track** — `remove_track` asks one question that the index alone cannot answer, so it is asked **before** the removal: *was this the track that was playing?* Two states arrive at `current_index = None` and mean opposite things — "the index I had is gone" and "there was never an index" (a direct open from the Library). Keying the unload on `current_index.is_none()` could not tell them apart, and both halves were wrong: removing the *playing* track cleared `current_path` while the sink kept running (audio with no Now Playing entry, and `advance`'s `current_path` guard refusing to move on), while removing any *unrelated* row during a direct open cleared `current_path` for the file that was actually playing. So the answer is `was_current`, computed up front: true → `stop()` (the sink, the xf, the position, the history, the pending spool); false → only the index shifts, and what is playing is untouched. Pinned by the pair in `playlist_edit.rs`, mutation-checked against the old body; `drag_drop.rs` covers only the index arithmetic and says so.
- **Every action is in one toolbar above the list** — the content ops on the left (a **text** "Sort by…" `ComboBox`, then the `Icon::Reverse` and `Icon::Shuffle` icon buttons) and the two file actions hard right (`Icon::NewList`, `Icon::Save`), each icon carrying a tooltip, because an icon-only button is otherwise a mystery. A plain `ui.horizontal`, not a wrapping one: the text labels were ~500px wide and blew the 320px minimum, while at `TOOLBAR_ICON` (16) the row is ~210px. The right pair is a `with_layout(Layout::right_to_left(egui::Align::Min))` block — **Min, not Center**, see `list_header_right` — and right-to-left means the *first* widget added lands furthest right, so **Save is added first** to read Create → Save. **The pane has no footer bar**: the ScrollArea takes everything `available_height()` has left, so there is no hardcoded `footer_h` to keep in sync and no row after the list whose space has to be reserved.
  - **The sort control is the one control that keeps its text, and text is the right call for it.** It is a `ComboBox` because it picks a column out of `SORT_OPTIONS`, and an icon could only say "something about order" — `sort_asc`/`sort_desc` mean the Library's *active column direction*, a different piece of state, and there is no third arrow to spend (an `Icon::Sort` was generated, judged a mystery box, and **deleted** rather than left as dead weight). The label is always "Sort by…": the ops are one-shot, so there is no standing order for it to report, and the dropdown is where the column names live. That also means **no `PL_SORT` egui-memory key at all** — a combo that displays a constant owns no state.
  - **Randomize reuses `Icon::Shuffle`** — randomizing once *is* a shuffle, and the mark already means that on the transport row. `reverse`/`new_list`/`save` came in with the toolbar. **`reverse` took three attempts, and all three failures were about collision with a mark that already exists** — two horizontal arrows pointing opposite ways read as `shuffle` (two crossings look like two directions), and a single left arrow shared a silhouette with `prev` (a bar plus a left triangle), which is the one mark "back to front" is most likely to be mistaken for. It is now **one arrow up and one arrow down** (a `⇅`, from game-icons' `vertical-flip`): vertical is the axis nothing else in the set uses. **`new_list` is the eight-ray sunburst the old generator drew** (8 rays from 40% out to 90% of the radius, no core) — kept, because `delapouite/files` (stacked pages) turns to mush at 20px, a ring of chords reads as a solid token, and a plus says "add" — the wrong verb for a button that *creates* an empty playlist rather than adding to the current one. The seven hand-authored icons are listed in `CREDITS` alongside their 16 upstream siblings; **`crossfade` and `shuffle` are the pair that had to diverge**, since they are 20px apart in the same pane and two crossing marks read alike: crossfade is two *smooth* S-curves crossing once (the textbook fade handover), while shuffle is the *angular* two-lane swap with two arrowheads.
- `the_playlist_pane_leaves_its_list_the_height_it_was_given` (`gui_tests.rs`) runs the **real pane** in a headless `Context` and asserts its `min_rect` still claims the window it was handed, at **both** the default and the minimum size. That is the only thing standing between this pane and the `list_header_right` failure mode (a `with_layout` under a vertical parent reporting a min_rect spanning the parent's whole remaining height), which collapses the list to the `.max(40.0)` floor *silently*; the test is mutation-checked by swapping the toolbar for the offending layout and watching it fail.
- **Jump-to-file** (`tplay.playlist.query`) — the same box, the same hint and the same title·artist·album+filename haystack as the Library's filter, and the same one-fold-the-case contract: the caller trims and lowercases the query once per frame, `row_matches` lowercases the haystack. It is a **`pub fn` free of any `egui::Ui`**, so `playlist_search::*` in `gui_tests.rs` tests the matching without a window. **The filter skips a row, it never reindexes the list** — the loop variable stays the true playlist index, so the row banding, the ✕, the click and the drag all act on the track that is actually there. A filtered-out list says "No tracks match"; an empty one says nothing, because that is already obvious. An empty query short-circuits inside `row_matches`, which is also what keeps an unfiltered list from building a haystack string per row per frame.
- **Content ops** — three one-shot edits, no standing order and nothing persisted: `app.sort_playlist(col)` (a `library::SORT_OPTIONS` index, so the playlist orders exactly like the file list beside it; untagged tracks fall back to the stem, which is what makes the columns usable while the tag scan is still filling in), `app.reverse_playlist()` (stdlib `Vec::reverse`, no helper), `app.randomize_playlist()`. The ordering half is `src/playlist.rs` (pure, tested); the app's half is one private `playlist_reordered()` that every op calls, because the *repairs* are the whole job: `playlist_dirty`, `reset_shuffle()` (the `played` history is a list of positions in the old order), `cancel_xf()` (a live crossfade's incoming track is pinned to an index that just moved), and **`current_index` re-found from the track *id*** — stable across a reorder (a local path or an `smb://` URI alike) and exact because playlist ids are unique. That last one is the whole point: without it a sort moves the highlight off the row that is playing and `advance` carries on from whatever track slid into the old index. It is gated on `current_index.is_some()`, because a direct open (`play_file`) has no index to follow and must not acquire one — that would silently enrol the track in the sequential flow. Mutation-checked in `playlist_edit.rs`.
- **Duplicate ids are dropped on load, not by a button.** `apply_playlist` calls `playlist::dedup` after `tracks::normalize`, and that is the *only* place one can arrive: `add_files` dedups as tracks go in, so a repeated path can only have come out of the file being loaded. A "Remove duplicates" menu item was considered and dropped as near-dead code with an honest alternative chosen instead. It also makes `position()` in `playlist_reordered` unambiguous.
- **Shuffle algorithm** (in `app.rs`): `peek_next_index` picks a random unplayed index (XorShift64) **without recording it**, `commit_next_index` records it, and `next_track_index` is the two composed — see **Shuffle order** below for why the split is load-bearing. `prev_track_index` is split the same way (`peek_prev_index` + `commit_prev`). `repeat=true` restarts the cycle when the pool is exhausted. `reset_shuffle()` clears `played` — called on toggle, play_track, remove/move, load, stop.
- **Drag-and-drop reorder**: `drag_from` / `drag_hover` live in egui Memory (`tplay.drag_from`, `tplay.drag_hover`) and persist across frames. On drop, item is removed from `from` and inserted at `to` (no `-1` adjustment), so dragging item 1 over item 3 puts it at position 3. `current_index` updated to follow the moved track.
- **Both drag indices are bounds-guarded, because egui clears temp state at shutdown rather than per frame** — so a press index outlives the rows that produced it, and `apply_playlist` is the reachable way that happens (an in-flight remote `.tplay` lands on its worker thread at an arbitrary moment). `Vec::remove` panics on an out-of-range index and a panic here is a dead process, so a stale index is dropped. `to` is bounded by the list **before** the removal, which is what makes "drag item 1 over item 3" mean position 3: the `remove` has already shortened the list when `insert` runs. This is the same hazard the armed `ConfirmAction::RemoveTrack` index guards at its call site, and that guard is the reason to believe the hazard is real. `drag_drop.rs` cannot hold this one — a guard is not index arithmetic, so there is nothing to mirror; it lives in `playlist_edit.rs` as `a_stale_drag_index_is_a_no_op_rather_than_a_panic`, mutation-checked by removing the guard.

## Tracks: one surface per source

A local track and an `smb://` track differ in exactly one way: **timing**. A local track's bytes
are on disk now; a remote track's may be in the spool cache, or may need a fetch first. Everything
else — the id, its tags, "does it exist", "give me the file to decode" — is the same operation
over a different transport. `src/tracks.rs` is where that is expressed, so **no part of the app
branches on where a track came from**.

- **`PathBuf` is the id, deliberately.** A `smb://` URI is stored as a `PathBuf` holding the URI,
  and a URI's last segment is the filename, so it works as an id with no help: the `tag_cache` is
  keyed by it, and `title_or_stem` / `sort_key` / `is_playlist` and the search haystack all treat a
  URI and a local path alike — which is exactly what makes one shared `file_list_ui` possible for
  both browsers. A `Track` newtype would be a rename-only diff across `playlist`, `.tplay` JSON,
  `config.json` and ~20 comparisons, removing no divergence.
- **`is_remote` is called from two places only**: `tracks.rs` (every track operation) and
  `library.rs`'s `read_playlist` mapper, where the question genuinely is about path semantics.
  **Never** from `app.rs` or `src/gui/`. Two `is_remote` branches survive in `app.rs`, both
  *playlist* concerns rather than track ones: the remote `last_playlist` restore and
  `save_playlist_to`.
- **The app holds one path per track, and never learns a local path exists.** The readable rule
  is "no `is_remote` in `app.rs`", but that was too weak: an earlier version resolved in the app
  and passed the pair around (`load_file_as(local, display)`), which passed the grep while still
  circulating two paths for one track — correct only if the caller does not swap them. It *was*
  swapped, twice, and `File::open("smb://…")` fails silently rather than loudly, so each swap was a
  quiet, app-killing bug. Hence the readers: `open`/`info`/`probe`/`cover` take a track id and
  return the thing asked for, and `is_ready` is the pre-buffer **predicate** so the pre-buffer
  question cannot yield a path either.
  **The enforceable form of the rule:** `app.rs` and `src/gui/` never call `File::open` /
  `read_info` / `probe_duration` / `read_cover` / `local_file*` on a track id, and never bind a
  resolved path. The app's whole track-I/O surface is those five functions plus `normalize`.
  `local_file_in` and `local_file_now_in` stay separate underneath, and the split is load-bearing:
  they agree everywhere except a *local* track with no file on disk, where `local_file_in` still
  yields the path (art and tags should be attempted, and the reader reports its own failure) and
  `local_file_now_in` yields `None` (there is nothing to pre-buffer). Collapsing them either blanks
  the art and tags of every track that fails to open, or makes `advance()` read "no file to
  pre-buffer" as "this is a remote track". Every reader has an `_in(dir)` twin so tests inject a
  spool dir and stay hermetic.
- **`play_now(track)` is the only way a track starts playing** — bytes on hand are loaded
  directly, otherwise it is requested and played on arrival. `play_file` (direct open,
  `current_index = None`) and `start` (playlist flow) differ *only* in the `current_index` they
  set, which is why that stays with the caller. `play_now` → `start_track(track)` is one
  parameter, so there is nothing to swap; that is deliberate, since the two-parameter version is
  what the crashes came from. `Event::Spooled` calls `start_track(uri)` like every other caller, so
  "the bytes just landed" is not a special case. (`play_now` is deliberately not named
  `play_track`; that name is the Playlist pane's "play row N" verb, which also resets shuffle.)
- **`normalize`** turns a playlist entry into the stored id: a local path is canonicalized and
  dropped if it no longer exists (a playlist must not resurrect a deleted file), and a remote URI
  is kept **verbatim** — rewriting it would break the spool-cache key that both playback and tag
  lookup use.
- **Gapless/crossfade follow availability, not source.** The xf arm asks `is_ready`, so an
  already-spooled network track crossfades like a local one; an uncached one cannot pre-buffer and
  falls through to a natural-advance gap — the same thing a local track with a missing file
  already did. Pinned by `pre_availability_decides_pre_buffering_not_the_source`.
- **Nothing on a per-frame path may abort the process.** `transition::build_gapless_next` returns
  `Option` and logs; it used to `.expect()`, which meant an unreadable incoming file killed the app
  from inside `advance()`. A crossfade is a nicety — failing to pre-buffer must cost a gap.
- **The pending state was already uniform.** `current_path.is_none()` plus `Network::pending()`
  is how the app knows a track is in flight, and that predates this section. Only the *entry
  point* used to fork.
- **The two remaining `is_remote` sites in `app.rs` are playlists, not tracks** — the remote
  `last_playlist` restore and `save_playlist_to`. They move a `.tplay` file, where the question is
  genuinely about path semantics, so they are left alone. `load_fetched_playlist(uri, local)` is
  the same shape and is deliberately still a pair.
- **The two tag transports stay two transports** — a thread with an mpsc, and a worker command
  with a reply `Event`. `TagReader` hides the split from callers without pretending the
  underlying machine is one thing.

## Visualizer
 
- Dockable pane (**Visualizer**), closed by default, auto-listed in the ☰ menu. No new theme tokens, no new icons.
- Header: the view selector is a dropdown (`ComboBox`) iterating `VizView::ALL`, persisted in `config.json` (`viz_view`) so the choice survives restarts.
- **Views are modular, mirroring the panes pattern**: one file per view under `src/gui/panes/visualizer/views/`, each exposing a single `pub fn draw(painter, rect, viz, palette)`; `visualizer.rs` is the dispatcher (header + one table lookup). Views own their per-frame state privately in egui memory (each keeps its own smoothing/history key, so nothing is shared and a view needs no registration beyond the table row). **Adding a view** = a new `views/<name>.rs` + a `VizView` variant in `config.rs` (`ALL` + `name`) + a `SHADER_VIEWS` row — no coordinator or config-file changes, and `gpu.rs` is never touched. `tests/app_integration.rs` pins `ALL`'s length and contents, so that test is part of adding one. **The dispatch is a lookup, not an exhaustive `match`**, which trades the compiler's "a new variant with no arm does not build" for a test: `every_view_has_a_shader_and_the_table_covers_them_all` checks *both* directions, because a `VizView` the table does not name is a view that appears in the dropdown, is written to `config.json`, restores across sessions, and draws nothing.
- **Every view is a fragment shader.** All nine, with no CPU-drawing half left — which is the point of the arrangement rather than an accident of the migration. One code path means one set of failure modes, and no question about which looks survive a driver that cannot compile one of them. The cost is real and stated plainly: a driver that cannot compile a shader now loses the whole pane rather than four views of it. Everything below is the harness; a view touches none of it.
  - **What the conversion bought, in concrete terms.** `chladni.rs` was the expensive one: 2 401 lattice samples of a field, a marching-squares pass over 2 304 cells, ~1 200 segments each expanded to a quad inside a hand-built `Mesh` — about **71 µs a frame**, the most expensive view in the set by an order of magnitude, all of it to decide which fragments to paint. As a per-fragment evaluation it is four sines and no search. `spectrogram.rs` repainted all 8 192 cells of its history sixty times a second to show a picture that had changed in one column; the history is now an image that shifts. `wave.rs` emitted ~1 500 primitives a frame for a shape that is a function of x.
  - **The convexity class of defect is designed out, not tested for.** It was a large amount of the old code, and it is written up in full under **Why this pane has no `fill_quads`** below because the rule is expensive to relearn. A fragment shader rasterises by deciding each fragment's colour, so there is no fan, no inset, no shared edge between two adjacent pieces and no tessellator to get wrong. `no_view_paints_anything_with_egui` is the cheap guard that says so, and the whole `view_fills::*` group went with the rule.
  - **`gui/panes/visualizer/gpu.rs` is the only file that touches `wgpu`**, and it names no `VizView`. Both halves of that are enforced, not documented — `the_wgpu_harness_never_names_a_view` and `every_view_has_a_shader_and_the_table_covers_them_all` read the source, because a harness that grew one view's uniform would compile, pass every behavioural test, and render correctly. Every `wgpu` symbol arrives through `eframe::egui_wgpu::{self, wgpu}`, never a bare `use wgpu` — see the dependency table for why a second copy would not merely duplicate, it would not compile.
  - **The one line that still divides the work: DSP on the CPU, drawing on the GPU.** `compute_bands` is 17 µs a frame and is covered by `viz_tests.rs`; a hand-written FFT in WGSL would cost a buffer upload per frame to save 0.1% of one, and would move the only part that can be tested headlessly into the only part that cannot. So a view computes its inputs in Rust and receives them as uniforms. **State that has to survive a frame stays on the CPU too**: the Chladni read's time constant and each view's attack/release smoothing are cross-frame state, and a shader would need a feedback target to hold either. What the GPU is for is a per-fragment *field* problem, and after this conversion every view is one.
  - **The uniform block is a fixed superset, and it is finished.** `Uniforms` is every input a visualization may ask for, and the whole block is uploaded unconditionally every frame. Under GLSL that was free because the compiler stripped what a shader did not reference; under WGSL nothing is stripped, and it is still the right shape, because one `struct` and one bind group serve every view — so a look reading two of the fields costs nothing, and a look needing a *new kind* of input is the only thing that may edit `gpu.rs`. That is a harness decision, not per-view boilerplate.
  - **Every member is a `vec4`, and that is the load-bearing part of the block.** WGSL gives an array in the uniform address space a **16-byte element stride whatever its element type**, so `array<f32, 32>` costs 512 bytes rather than 128. A block packed 4 bytes per `f32` is then read as garbage — *silently* garbage, because naga validates the shader against the shader and the buffer is ours. So both arrays are `array<vec4<f32>, N/4>` and every scalar rides in a lane, which is why `VIZ_BANDS` and `WAVE_BUCKETS` must both be multiples of four. `Uniforms::write_block` is the single writer, `wgsl_struct` the single declaration, and `the_wgsl_uniform_layout_is_the_block_this_code_writes` compares the two against **naga's own `Layouter`**, so the two halves cannot disagree.
  - **The block is nine scalars and two arrays, and the VU meter's deletion took four of its fields with it.** It carried `u_hold`, `u_slider_track`, `u_border` and `u_level` — a peak-hold position, a rail, a graticule hairline and the loudness pair — all for one view, which was the sole reader of every one. `u_level` was the expensive half: `pack` filled it from a full pass over 4 096 samples on **every frame of every view**, for a uniform no shipped shader declared. **A uniform block should be expected to shrink, and a deleted view takes its inputs with it.**
  - **The block's size is now checked against what the API actually says, and the old ceiling is gone with GL.** `WAVE_BUCKETS` is **128** and was chosen under GL 3.3 core, which promises only `MAX_FRAGMENT_UNIFORM_VECTORS >= 224` while letting a `float` array's elements take a whole `vec4` slot each; 128 + 32 was 160 vectors and 256 buckets would have been 288. Under wgpu the guarantee is expressed as `max_uniform_buffer_binding_size`, which a *block* is bounded by rather than an array, and `Limits::downlevel_defaults()` covers 736 bytes by six orders of magnitude — so the old reasoning no longer applies and neither does the test that encoded it. `the_wgsl_uniform_layout_is_the_block_this_code_writes` asserts the real property instead: naga's computed layout equals `Uniforms::BLOCK_BYTES` and every member is a `vec4`. It deliberately does **not** hardcode the array sizes, for the reason the GL version's did not — a test that copies the constant it is checking reports the right number whichever way the constant moves.
  - **The prelude is generated, and unconditional.** `wgsl_module` `format!`s the block declaration, the `@group(0) @binding(0)` uniform, the constants, the accessor functions and the shared helpers, then the body. `VIZ_BANDS` and `WAVE_BUCKETS` are interpolated, so an array cannot drift from the DSP — a literal would fail *silently* — and a shader cannot reference an input the harness does not upload, because the harness owns the list. **The filtering is deleted, and that is a wgsL-shaped simplification rather than a nicety:** the GLSL version emitted only the declarations a body mentioned, because the compiler stripped the rest anyway. WGSL strips nothing and a declared-but-unused binding is free, so filtering could only ever have introduced a bug — a body whose helper needed an input the filter did not know about. **A shared helper therefore brings its own inputs with it and lives in `ShaderView::helpers` rather than in the prelude**, because WGSL has no nested functions: the five views that need their own helper would otherwise each have to be special-cased in `gpu.rs`, which is the one thing this arrangement forbids. The accessors are `band_at` / `wave_at` / `u_resolution` / …, named to leave `band` free for a view (`flame` defines one).
  - **The prelude carries a shared `level()`, and the number in it is a boundary between two halves that cannot see each other.** The dB → 0..1 mapping was a hand-written `float level(float d)` in **six** view bodies plus two inlined copies — all correct, all separate — and it is *derived from* [`DB_FLOOR`] rather than typed, so a floor that stops being half the ceiling cannot leave a literal span behind. The failure this prevents is invisible in the only way that matters: the DSP clamps into `DB_FLOOR..=0.0` and the shaders map out of it, so a one-sided edit still compiles, still runs, and still returns in-range values — it just quietly compresses or clips each view's quiet end, differently in each one. **The Rust side had nine more copies of the same number**, as a view's smoothing-buffer seed, and a seed at a level `compute_bands` can never produce means every view's *first* frames are wrong with nothing to compare them against; those are `[DB_FLOOR; VIZ_BANDS]` now. Pinned by `the_db_floor_is_one_number_across_the_dsp_and_every_shader`, which reads the **assembled** module for the value and the view **sources** for a literal — the first version of it read only the shader and a retyped Rust seed passed it.
  - **The prelude also carries a shared bearing projection, and the reason is a trap three views fell into.** `spectrum_at_bearing(p)` is how a view reads the spectrum *as a function of a direction*. The obvious spelling is `atan(y, x)` scaled and floored into `u_bands`, and **`atan` has a branch cut**: it jumps from `+pi` to `−pi` along `x < 0` at `y == 0`, which is a fixed line up the middle of the pane's left side. So the band index steps there, and whatever the index drives steps with it. **No edge fade can hide that, and that is the whole reason it is a rule**: a fade takes a value to zero at a *boundary*, while this is a break in the middle of the *function* — the two sides are different colours, and the best a fade can do is smear between them. `Plasma` and `Trails` both shipped it and both showed it as a seam on the left; in `Trails` it was worse than a seam, because `fresh` is *added* to the buffer every frame, so the step was **deposited** as a permanent line. The projection is the same shape of read (`R * cos(a - phi)` for two coefficients, plus a second harmonic so the result is not symmetric under a half turn) and is continuous and periodic by construction; the `max` guarding the pane's centre is a `max` rather than an `if` **because a guard has to be as continuous as the thing it guards** — a branch there would put the discontinuity somewhere new. It lives in the harness because the alternative is three copies of a hazard, and a copy can be got wrong in a way the original cannot; and because `a_shader_never_indexes_a_band_through_an_angle` can then forbid the broken form outright, so a new view wanting a radial read finds one path instead of rediscovering the trap. The helper pulls in `u_bands` and `VIZ_BANDS` itself, so a body that only calls it still gets its declarations — **that coupling is why the helper lives beside `declarations()` and not in a view.**
    - **`Radial` is the stated exception, and it is a real one.** Its *layout* is angular sectors — one band per sector — so indexing a band by angle is the picture rather than a means to it, and its cut lands exactly on the segment gap the view already draws (`in_band` is zero for `within < 0.05` on both sides), so there the break in the layout is not a break in the picture. **Do not "fix" Radial**, and do not widen the exception to any view that merely mentions an angle: the test names it.
  - **One vertex shader, shared, and it is where the uv comes from.** A fullscreen triangle needs no attributes, so `@builtin(vertex_index)` synthesises its corners and the module contains no vertex buffer. It also computes the `uv` varying every view reads: the viewport is set to the pane, so NDC −1..1 *is* the pane and the oversized triangle's own corner is already the 0..1 fraction, with `y` flipped because the fragment stage's own position is bottom-up while every view reasons top-down. A new look is therefore *only* a fragment shader body.
  - **No view may read the built-in fragment position, and the reason is the worst bug this pane has had.** It is **window-relative and bottom-left origin**; every view here is pane-relative and top-down. Nine of ten views divided it by the pane's size as though it were neither, and one mistake produced six unrelated-looking symptoms — bars frozen on a seam where the quotient saturated, rings off-centre, a ridgeline upside down, the nebula's raymarch starting outside its own volume so the pane went blank. **Every headless test passed the entire time**: the shaders validated, the callback count and rect were right, the pipelines linked, the driver reported nothing. It took a person looking at the window, which is the instrument this project does not have. So it is pinned by `no_shader_reads_a_window_relative_pixel_coordinate`, which asserts **both** halves — that the shared vertex stage still hands over the top-down pane-relative `uv`, and that no body reaches for `in.pos` or the vertex index — and is mutation-checked on both. Under WGSL the trap is quieter, not louder: there is no `gl_FragCoord` *name* left to grep for, so the test matches the builtin and had to be renamed with it.
  - **An offscreen pass fills its whole target, not the pane's window rect.** The callback's viewport and clip are the pane's rectangle in *window* coordinates, which is right for the default framebuffer and wrong for an owned one — a framebuffer's viewport is its own space, so the accumulate pass wrote at a scroll offset inside the texture and dropped whatever fell outside it. The quantised target is then up to one grid cell larger than the pane and `v_uv` spans all of it, so the present pass upscales by that much and nothing more.
  - **`Shape::Callback` is a documented contract, not a hack — but only the *clip* half of it survives wgpu.** `epaint` states that the backend sets the viewport to the callback's rect and **restores any state the callback changed**. egui_wgpu honours the second clause literally (`prepare_painting` runs under a `// Restore state` comment after every callback) and **does not honour the first**: `renderer.rs` sets the viewport to the whole surface. So the harness sets its own viewport to the pane in `paint`, and leaves the **scissor entirely alone** — egui_wgpu already clipped to `info.clip_rect` for this primitive, and it owns putting both back for the next one. A wrong viewport here is invisible: the view paints over the window instead of into its own rect and nothing complains.
  - **A pipeline build failure degrades to the background, once.** The pipeline cache stores `Option<Entry>`, so a `None` is a *recorded failure* rather than a miss — a driver that cannot build would otherwise be asked again 60 times a second, and a build is a driver round trip and a log line. **This is also why the blank pane was such a bad symptom to debug by eye:** a broken shader and a working one both render as the background, so the failure is indistinguishable from the success case by anything you can see. `eprintln!` goes to stderr, which is where to look first.
  - **There is no GL floor to state any more, and that is one of the nicer things about the port.** `glow` had to name an exact version (a *second* copy could not unify) and a `#version 120` twin would have been a second copy of every body for hardware that does not ship. wgpu has neither problem: it is reached through `eframe::egui_wgpu`, so the version is whatever eframe resolved, and there is exactly one WGSL dialect.
  - **Every shader is validated by a test — `every_shader_validates` — in process, on every machine, CI included.** It runs **`wgpu::naga`** (re-exported by the `wgpu` dev-dependency, so it names nothing new) over `gpu::wgsl_module`'s own assembled output plus the shared vertex stage, in the same configuration the device is built with. **This replaces a `glslangValidator -l` invocation that *skipped* when the tool was absent**, so it was skipped in CI by construction and ran only on developer machines that happened to have a Vulkan SDK. The three defects it caught on the first day all rendered as a blank pane — the exact same symptom as the documented "no GPU here" fallback, so every other instrument was blind to them. (1) A function named `noise3`, which is a **GLSL built-in** (`vec3 noise3(vec3)`); overloading it with a `float` return is a hard error, and glslang words it "overloaded functions must have the same return type", which reads like a duplicate definition and is not one. `noise2` is the same. (2) `p *= 17.0;` on a function **parameter** — GLSL parameters are `in` and read-only, and `inout` is no escape because every call site passes an expression. (3) A forward reference, which `every_glsl_function_is_declared_before_use` covered on its own and **WGSL makes impossible** — there are no declarations, only functions — so that test is **deleted rather than ported**. The general lesson is unchanged: **a shader is a string and every property of it that matters is a property of the string.**
  - **And now that a driver is reachable in process, the strongest test needs no shader at all.** `the_callback_paints_the_pane_and_nothing_outside_it` builds a real headless `Device`, hands the **exact object the pane queues** to `prepare` and `paint` against an offscreen 256 x 64 texture cleared to a colour no palette produces, and reads the pixels back. Two claims: something was drawn, and **nothing outside the pane** was — which is the viewport, because a fullscreen triangle has no vertices and the viewport is the only thing bounding it. It **skips, rather than fails, where there is no adapter**, because a hard failure on a missing device gets the test deleted; CI installs `mesa-vulkan-drivers`, so lavapipe runs it on every tagged build. This is the first test in the repo that can see the difference between a shader that draws and a shader that silently writes nothing, which is exactly the failure the whole `gl_FragCoord` story above is a long example of.
  - **`SHADER_VIEWS` must name the source the app actually ships.** It was briefly wrong: Trails listed the unsubstituted `ACCUMULATE_BODY` while the program cache keyed on a `LazyLock` that textually replaced two constants — so the table named a shader the app never ran, which is precisely the drift the table exists to prevent, and the substitution machinery caused it. The constants are now literals in the body with the value and the reason in a comment beside them. Two numbers in a shader body is a smaller risk than the machinery guarding them. **What *is* tested of the CPU half**, because it all happens in `draw`: `every_shader_view_asks_for_exactly_one_callback` runs the real `draw` in a headless `Context` and asserts a single `Shape::Callback` at the pane rect, the same technique as `the_playlist_pane_leaves_its_list_the_height_it_was_given`. Every sweep runs off `views::SHADER_VIEWS`, so a new view is a table row and not a test body.
  - **A shader that is too expensive does not draw slowly — it stops the window presenting.** Nebula's first version asked for 10752 noise evaluations per fragment (7.7 billion a frame at 720k fragments), because a two-round **domain warp is quadratic in `fbm` calls** — seven per sample — evaluated inside a 48-step march. It is now one `fbm` call, three octaves and 24 steps (576 per fragment, 18x cheaper), with the arithmetic written into `main` beside the step count. `no_shader_marches_further_than_it_can_afford` bounds it — `fbm` call sites x the largest step count, plus a hard step ceiling. **That test started as a call-graph cost estimator and was deleted**: it was wrong twice, both times in the direction that made it *pass*, which is worse than no guard.
  - **The cost budget has a ceiling nothing in the app enforces: the app repaints only when `scanning || network.busy() || is_playing()`.** Nothing about the visualizer is in it, so a view's frame rate is the app's frame rate and a view cannot ask for one. Measured on the machine this was reported from: **120 passes/s at 0.3 ms per pass for a 0.10 Mpx pane** — so the whole budget for a view is 0.3 ms of a 8.3 ms frame, and any view wanting more has to take it from the app. `gpu::probe` measured that and is now **removed**; it was one function and three lines, sampled one pass in 120 with a pipeline flush (the only in-process way to see what the driver did, since GPU commands are queued), and it stalled the pipeline once a second, which is a real hitch for a number that has been read. The lesson is not the probe, it is the two rounds it took to add: **the missing measurement was the wall clock, not the GPU cost** — 0.3 ms of GPU established the shader was innocent and said nothing about frame rate, and the frame rate was the whole answer.
  - **A feedback view leaks and thrashes unless its target sizing is designed, and both halves are quiet.** `Fbo` **cannot implement `Drop`** — destroying a GPU resource needs the device, which `Drop` cannot reach — so a replaced target's texture and view leak unless something holding the device frees them. `Feedback::create` therefore destroys the pair it replaces, *in the callback*. The other half is `target_size`, which is where the churn came from: the pane rect is in **points** while the screen is in **physical pixels** (a quarter of the area at 2x, so the trail drew at quarter resolution and looked like a soft smear), and a dock's pane rect **jitters by fractions of a pixel** as a splitter settles. An exact size check reads that jitter as "wrong size", so every jitter rebuilt both targets — and each rebuild leaked the pair it replaced, tens of megabytes a time, sixty times a second. So the size is quantised to a 64px grid: coarse is free on a soft accumulating trail, and being wrong by a pixel *every frame* is not. A creation **failure** is recorded and never retried, the same lesson the program cache already had. All four are mutation-checked.
  - **Per-view `ATTACK_MS`/`RELEASE_MS` are time constants in milliseconds, and that is a bug fix, not a preference.** They were per-frame *fractions*, which is the same frame-rate-dependent shape `feedback_for_a_dt` and `PLATE_TAU` were both converted away from — see those two bullets for why the trap is easy to fall into and hard to see. A fixed fraction per frame converges `hz / 60` times too fast on a faster display: at 60 fps the bars' `0.3` attack closes in 47 ms, on a 120 Hz display the same `0.3` closes in 28 ms, and on a 240 Hz one in 14 ms. **So the panes judder worse the faster the display is**, which is exactly what was reported and exactly what no screenshot shows — a screenshot has no refresh rate.
    - **The numbers a percussive spectrum forces.** Measured on real audio, a band moves up to **~10 dB between consecutive frames**, which at the pane's 343 px height is ~57 px of bar travel; the shipped attack of `0.3` closed 30 % of that per frame, so ~17 px per frame. On a 240 Hz display that is 17 px every 4 ms. Bars is the view that shows it most plainly because it is 32 plain heights with no history and no feedback — the shader is not involved at all.
    - **The safety property, which is what makes this changeable without looking at it: at 60 Hz the derived coefficients reproduce the old fractions to within a rounding error** (46.7 ms → 0.300, 6.6 ms → 0.920, and so on for all seven views' pairs). A 60 Hz display is therefore *unchanged*, and only faster ones move. `the_band_smoother_is_a_time_constant_and_not_a_frame_fraction` (`viz_tests.rs`) pins exactly that, and it pins the real invariant rather than a ratio: `a` is nonlinear in `dt`, so halving the frame does not halve the step (0.92 → 0.72 for the fast release), and the claim worth making is that **inverting the coefficient returns the time constant the view wrote down, at 144, 120, 60 and 30 Hz alike** — frame-rate independence as an equation. The `dt <= 0` guard holds rather than snaps, for `feedback_for_a_dt`'s reason.
  - **The clock those constants are measured against is ours, because eframe does not supply one.** `predicted_dt` is documented as "the time delta egui should assume", and eframe 0.36's `prepare_raw_input` sets `time` and calls the app's `raw_input_hook` **without ever touching `predicted_dt`** — so it keeps `RawInput`'s default of `1.0 / 60.0`, and because `pending_raw_input` is `mem::take`n each frame the default is restored every frame. **The field is therefore a constant 16.67 ms in every eframe 0.36 app**, measured at a rock-steady `0.01667` on a 120 Hz output whose frames were 8.33 ms apart. That is 2× wrong at 120 Hz and 4× at 240 Hz, and it feeds `u_dt`, so `trails` decayed a quarter as fast as `HOLD_SECS` names and `chladni` followed a quarter as fast as `PLATE_TAU`.
    - `TPlay::raw_input_hook` measures the real interval and writes it. The policy is `app::frame_dt_from(prev, now) -> Option<f32>`, and it returns `None` — leaving egui's default alone — for a first frame (nothing to measure), a clock that did not move (`0` is read as "hold" by every smoother here, so reporting it would freeze the visualizer *and keep it frozen*), and a gap too long to be a frame (a window drag, a resume, a first frame after a pipeline compile — 805 ms in a startup trace, which would make every per-frame smoother snap to target in one step). `the_frame_clock_believes_a_frame_and_rejects_everything_else` pins each rejection by the failure it prevents.
    - **This is why the two fixes are one fix.** With egui's fake 16.67 ms still in place, the band smoothing derived `0.300` from a 46.7 ms time constant — byte-identical to the fraction it replaced, and a no-op. Only the clock being real makes the time constants mean anything. Verified live on a 240 Hz display: `predicted_dt` went from a hardcoded `0.01667` to a measured `0.00838`.
  - **An edge fade is keyed on the fragment's **own** coordinate, and the only two views that reach for a different one are the two that got it wrong.** `Trails`' fade was computed from `prev`, the coordinate it *samples* — but the trail shrinks toward the centre, so at the pane's left edge `prev.x` is about `0.502`, the middle of the picture. The fade therefore ramped through the middle, left the real edge at full weight, and the `clamp` then held that edge texel at full strength for the whole fade: a hard line where a gradient was intended. **What is being faded is the contribution, and the contribution is a function of where the fragment is**, so `uv` is the coordinate it belongs to. Pinned by `the_trails_fade_follows_the_fragment_not_the_sample`, which carries a premise guard: if `prev.x` at the left edge ever became ~0 the fade would coincide with the edge and the check would be reading a coincidence. This is the same "which space is this coordinate in" trap as the waterfall's `y` flip, and these two views are the only two in the set that use a coordinate other than `v_uv` — which is why both are pinned.
  - **The colour rule.** Every view's colour comes from the palette uniforms, so a theme switch moves all nine at once. A shader that hardcodes a colour is the one that does not follow — and nothing else in the app can see it. `no_shader_hardcodes_a_colour` covers `#rrggbb` and `rgb(...)`; a bare `vec3(0.2, 0.4, 0.9)` is **deliberately not matched**, because the eight lattice corners of a value-noise function are written `vec3(0,0,0)`..`vec3(1,1,1)` and no textual rule separates those from a colour. `every_shader_reads_the_palette` carries the weight instead: a shader that mentions no palette uniform ignores the theme just as thoroughly, and no pattern-matching catches that.
  - **Pane size is a correctness property here, and every view is now checked for it.** `v_uv` is 0..1 over the pane in *both* axes, so a view that treats it as a square space draws a correct picture of the wrong shape, and the distortion scales with how far from square the pane is. That is invisible in a screenshot — one size, and the default is close enough to square to look right — and the failure mode is a user dragging a splitter, which tests never do. Three distinct defects, all found by reading rather than by looking:
    - **`trails` had no aspect correction at all**, which is the worst place for that: it is a *feedback* view, so the error is not one distorted picture but a different transform every frame folded into the buffer. The ring drew as an ellipse, the per-frame spin became a **shear** rather than a rotation, and the zoom shrank by a different fraction per axis — compounding. It now makes the same `vec2(u_resolution.x / max(u_resolution.y, 1.0), 1.0)` correction the other four views already had, **and divides it back out before sampling**: `texture()` takes the target's own 0..1 space, so a corrected coordinate handed straight to it reads a mirrored point and shears the whole trail. That asymmetry — correct going in, undo coming out — is the same class as the waterfall's `y` flip.
    - **`flame` fed a raw `uv.x` into a Gaussian** whose height is measured in pane-height units, so the cross-section stretched on a wide pane and pinched on a tall one. The shoulders and the tip changing shape with the splitter is the whole of what separates a flame from a bar.
    - **`bars` sized its gap and its tick as fractions of a cell**, so below ~6px per cell both went sub-pixel and the row shimmered as the splitter moved. Now read with `fwidth` — the same physical-threshold idea as chladni's `fwidth` line width — and the view **dims out below two pixels per cell** rather than aliasing. That fade is the one deliberate degradation in the pane: every other property is resolution-independent, and this is the case where the honest answer is to draw *less* rather than draw differently.
    - **The pane recorded no minimum size at all.** It is the only pane here that draws nothing but a fullscreen shader, so it has no measured content to floor it and `apply_min_pane_sizes` skipped it entirely — the splitter could drag it to a few pixels tall. It now states a floor derived from that same two-pixels-per-cell limit, with the header **measured** rather than written down twice (the EQ pane's slider budget once clipped its own labels by doing that).
    - **All four guards are source-reading, and that is not a shortcut — it is the only instrument available.** A full revert of the `trails` fix left all 48 `gui_tests` **green**: nothing crashes, the callback is still queued, the program still links, and no behavioural test can see a string. `a_view_that_draws_round_corrects_the_aspect_ratio` therefore asserts the corrected *assignment*, not that the file mentions `u_resolution` — a mention elsewhere in the file is not a correction, and that was measured too. `a_feedback_view_uncorrects_the_aspect_before_sampling` asserts the **round trip**, because the intermediate is a variable and the dataflow is one statement removed rather than a name changed. `a_view_that_cells_the_pane_declares_its_sampling_limit` asks whether a celling view ever asked how many pixels a cell is, which is a question about the *reason* and not about a number — a test pinning a named constant only proves the constant. `the_visualizer_floor_matches_the_bars_sampling_limit` is the one geometric claim, and it runs the real pane in a headless `Context` like the Playlist geometry test.
    - **Three of the first three guard versions were themselves wrong**, found only by mutating the source and watching for a failure rather than trusting a green run: a whole-file `contains` that a comment satisfied, a line-based check that a three-line expression escaped, and a search that matched `textureSize(` as if it were a sample. The mutation is the test.
  - **The tap delivers audio in bursts, and reading "the newest N samples" is stutter.** This is the cause of the judder, and it is not the frame rate, the shaders, or the smoothing — every one of those was measured and cleared first.
    - **Why bursts.** `TapSource::next` runs inside rodio's mixer pull, and the mixer is pulled by cpal's output callback, which asks for a whole `buffer_size` at once — 8192 samples, one call every ~186 ms at the shipped default. So `push` runs 8192 times in a burst and then not at all for the rest of the period.
    - **The measurement, and it is why no frame rate could have fixed it.** A reader taking the newest window saw **0 distinct spectra across 22 idle frames** at 120 fps: the picture froze and then snapped to unrelated audio. The discontinuity is in the data, so a faster frame only draws the same frozen picture more times. **It also explains why the judder got worse as the display got faster**: a 186 ms hole is 11 frames at 60 Hz, where it hides under the eye's persistence, and 22 at 120 Hz, where it does not.
    - **The fix is a read cursor** (`VizBuf::read_window`). The window ends at a cursor that advances by `rate * dt` rather than jumping to the newest sample, so one burst is walked out over the ~22 frames that follow it and each frame reads a slightly later slice. Steady state on the committed fixture: **220 of 220 reads produce a distinct spectrum**, with the largest step on a *burst* frame (5.25 dB) **lower** than off one (15.56 dB) — which is the claim that the jumps are gone and the remaining variance is the music.
    - **`VIZ_BUFFER_CAP` had to grow from 4096 to 16384, and that is load-bearing rather than tidy.** A ring smaller than one burst cannot hold the backlog, so the cursor outruns the ring, re-anchors to the newest sample, and the picture jumps again — measured at 8 distinct spectra over 22 frames and a 20.9 dB step with a 4096 ring. 16384 holds two default bursts. `config.buffer_size` is clamped to 512..=65536 in `main.rs`, so a hand-set 65536 would outrun it; that is a named ceiling, not a bug to design out.
    - Pinned by `the_read_cursor_turns_an_audio_burst_into_many_small_steps` (each read moves by about one frame's worth of samples, not the whole burst, and one burst must feed more than 15 frames) and `the_read_cursor_stays_inside_the_ring_and_resets` (the window is always a contiguous slice of the ramp, and `clear` resets the cursor with the ring). **Both mutation-checked**: snapping the cursor forward — the old behaviour — and shrinking the ring back to 4096 each fail the first.
    - **One read per frame may advance the cursor, and this is what blanked the spectrogram.** Every view calls `compute_bands` *and* `compute_wave` (the latter inside `Uniforms::pack`), so there are **two reads per frame**. When the second one advanced the cursor too, it consumed the arrival flag — and the two feedback views are the only two that call `take_arrival`. Trails kept its previous frame; the spectrogram, which has no history to fall back on, showed nothing at all. So `compute_wave` uses `read_window_peek`, and there are **two rules** on the flag inside `read_locked`, each of which was a bug:
      - **Only an advancing read may move the cursor.** A peek is handed `dt = 0.0`, so it cannot move anything even by accident.
      - **Any read folds a pending arrival into the flag, and only ever ORs.** Gating the fold on `advance` loses an arrival when a frame's reads all peek (the same blank by another route), and *assigning* instead of OR-ing lets the frame's second read overwrite a true with a false (the original blank).
    - **Those two rules are pinned by reading the source, not by behaviour** — `the_read_cursors_advance_and_report_rules_are_stated_in_one_place`. The reason is measured: a peek is handed `dt = 0.0`, so **making it advance moves nothing and every behavioural test still passes.** Three mutations of `read_window_peek` / `read_locked` survived the whole behavioural suite before this pin existed; all three now fail it. This is the same reason `the_wgpu_harness_never_names_a_view` reads a file: a rule about *which branch runs* is invisible from outside. The behavioural half is `a_second_read_in_a_frame_does_not_consume_the_arrival`, which replays the real `spectrogram::draw` order (advancing read, peek, take) over 240 frames and asserts a column on **every** frame — not one per burst, which would pass with the stutter back.
    - **A read, then a `take_arrival`, is the order, and it matters.** A push on its own is not reported: the read is what folds it into `advanced`, which is also what stops a burst being spent twice. `every_shader_view_asks_for_exactly_one_callback` drives the real `draw`, so it exercises the held path.
  - **A view needs its own egui-memory key**, and this is the one real trap: two views sharing a smoothing buffer means switching between them starts the new one holding the other's history. `every_view_keys_its_own_memory` reads the sources, so a key nothing claims cannot be flagged — which is what makes a *deleted* view's key a hole rather than an error.
  - **A feedback view is the one thing egui cannot express, and there are two of them:** `Trails` samples **its own previous output**, and `Spectrogram` keeps **its own history**. A `Painter` is a one-frame surface with no render target a view may keep reading from, so each renders into an owned RGBA8 pair (`Fbo`), ping-ponged, and presents in a second pass **inside one callback** — two `Shape::Callback`s would have egui restore GL state between them and the present pass would land over whatever landed in between. `Trails` is where the extra machinery was justified; `Spectrogram` is a row, not a subsystem. `Feedback` holds the pair behind a `Mutex` because the paint callback is `Fn` and cannot mutate a capture, so the creation pass writes through the slot and the next frame picks it up; the **first frame after a fresh, a resize or a view switch therefore shows the background**, which is the honest cost of a context that exists only while something is being drawn. A view switch is detected by a one-bit "was selected" flag, since nothing tells a pane it is no longer selected. Both silent-blank risks are pinned: `target_size` is physical-not-points, quantised so a 0.01px jitter cannot rebuild the pair (a zero dimension is `INVALID_VALUE` with nothing in any log, and a rebuild leaked it), and `feedback_for_a_dt` is frame-rate independent — a per-frame multiplier is a fixed fraction per frame, so a trail would be twice as long at 30 Hz as at 60 Hz, which no screenshot can reveal. Its `dt <= 0.0` guard is the sharp end: `exp(0.0)` is exactly 1.0, i.e. "keep the whole previous frame", and egui's predicted `dt` is legitimately zero on a session's first frame.
  - **A feedback view advances on audio, not on frames, and "paused" means held rather than blank.** The accumulate pass is the only thing in the whole pane that *moves*: the present pass just samples what the target already holds. So a feedback view's picture is a **record of audio that happened**, and the honest signal for "some happened" is `VizBuf::take_arrival`, which reports whether the **read cursor moved** — and the cursor only moves if audio arrived, because it advances by `rate * dt` and cannot outrun what was pushed. `push` has exactly one caller, `TapSource::next`, so while paused nothing is pushed and the cursor has nothing to consume. While a sink is paused the mixer is not pulling, nothing is pushed, and the view **holds its last frame**: the callback still runs, so the picture stays on screen. `Feedback::draw`'s `advance` argument gates only the accumulate, *after* the fresh-target clear — a cleared target has to be cleared whatever happens, because the present pass samples it either way. Parity does not flip while held, so a held frame presents the same target rather than alternating between the newest picture and the one before it.
    - **The first attempt gated the pane's dispatch instead, and it was wrong in a way only a person could have said.** Skipping `draw` while paused stops the feedback views dead — and blanks the pane, which reads as the feature *vanishing* rather than as the picture holding. The other seven views are pure functions of a buffer that is not changing, so redrawing them is free of consequence and they need no gate at all; **which is why the fix belongs to the two views with a history and not to the pane.** This is also the answer to "the frames are coming from somewhere": `update` already returned `false` while paused, so eframe/egui were asking for them, and only the pane knows whether a frame does any work.
    - `an_arrival_is_reported_once_and_only_while_audio_is_pushed` (`viz_tests.rs`) pins the three claims: a fresh buffer reports nothing, one push is one arrival (the `take`, so one frame's worth of history rather than one per viewer), and `clear` — which is what `stop()` calls — is not an arrival either. Its sequences are **read then take**, which is the app's order. The other half is pinned by `every_shader_view_asks_for_exactly_one_callback`, which drives the real `draw` in a headless `Context` over **both** arms — one arrival consumed, then none — so a held frame is a covered path rather than an accident of iteration order. It used to cover it by luck: `take_arrival` consumes, so `pane`'s 4096 pushes were one arrival, the first view in the sweep recorded audio and the other eight held. Mutation-checked by putting an early `return` on the held path, which reports `0 callbacks`.
- Audio pipeline: `TapSource` wraps `EqSource`, so the visualizer shows **exactly what you hear** (post-EQ). The tap, the ring buffer and the per-frame FFT are described under **Visualization tap source** in *Non-obvious machinery*.
- **Two DSP inputs, and a view picks one.** `compute_bands` is the spectrum (frequency, 32 log-spaced dB bands) and `compute_wave` is time-domain. **A third was removed with the VU meter**: `compute_level`, the loudness `(rms, peak)`, was the only reading of *amount* rather than *shape*, and nothing in the pane reaches it now. The function and its three tests are gone from `audio::viz` rather than left dormant — it was called once a frame over 4 096 samples to fill a uniform the deleted view was the sole reader of, so keeping it meant keeping a per-frame cost wired to nothing. Only one view is drawn per frame, so the FFT runs once regardless of how many views exist.
- **Bars view**: 1024-point radix-2 FFT with Hann window → 32 log-spaced bands → dB-normalized (-60..0) → per-bin attack/release smoothing (classic WMP feel). The window is a `static LazyLock` in `audio/viz.rs`, because it is a function of two compile-time constants: it used to be 1024 `cos` calls **per frame**, 60k/second, to recompute a value that can never change. Same rule as `EQ_BANDS` — anything whose shape is fixed is built once, at first use.
- **Wave view**: mirrored time-domain **peak envelope** downsampled from the ring buffer into `WAVE_BUCKETS` buckets over a ~23 ms window, drawn as one filled column with an outline on both edges. **The bucket count is a constant, not a pane measurement** — it used to be one bucket per 2px of pane width, and a uniform array's length is part of its WGSL declaration, so it cannot move with the splitter. 128 is a taste call under wgpu — the old GL 3.3 ceiling that fixed it is gone with the port (see the superset bullet).
- **Radial / Spectrogram** — the two that are `compute_bands` and nothing else, i.e. a re-projection of the same array rather than new DSP. **Radial** is a ring sector, which as a fragment is `step(inner, r) * step(r, inner + level * span)` and nothing else. Both were previously a `fill_quads` decomposition into convex quads, and the decomposition is gone.
  - **Spectrogram is a feedback view, and the history is the history in a texture.** It runs **two** programs: the accumulate must read its own history with **`texelFetch`** (whole texels) and the present must sample the same texture with **`texture()`** (interpolated), because the quantised target is a little larger than the pane it is stretched across. One program cannot be both, and the wrong one of the two is a picture that looks plausible and is wrong. **Three defects shipped with the first version, and none was visible to any check that existed** — the shader compiled, the callback count and rect were right, the program linked, the column count was right and the scroll genuinely happened. Two are pinned by `the_waterfall_scrolls_by_whole_texels` and `the_waterfalls_new_column_lands_where_the_scroll_vacated_it`; the third — the `y` convention, which is a **wgpu** fact rather than shader arithmetic — is `no_view_mirrors_the_pane_in_y` below.
    - **A scroll that resamples itself is a low-pass filter applied once per column.** The shift was `1.0 / 256.0` of the target's width through a LINEAR sampler — a *fractional* texel offset for every target width that is not a multiple of 256, and a fractional offset interpolates between two neighbours. Applied to the whole history once a frame, that is 256 low-pass passes over 256 columns. **And because the offset was fractional only on some widths, it read as a property of the window rather than of the code** — sharp at 256/512/1024, blurred at 320/640/896. The column width is now `max(1, sz.x / 256)` **texels**, so the shift is exact everywhere. The price, stated because it is real: the column count is the target's width over the column width, so the history spans a different number of seconds on a narrow pane than a wide one.
    - **The column the shift consumes and the column that gets overwritten are the same column.** The new column was written on the *left* edge while the shift moved the history *left*, so the leftmost column was overwritten every frame and never scrolled — a permanent bright bar down the wrong side of the pane, plus a second copy of the same column at the opposite edge.
    - **In wgpu, framebuffer row 0 is at NDC `y = +1` — the *top* — and `textureSample`'s `uv.y = 0` is that same row. So no pass flips `y`, and this was the worst bug in the port.** The GL-era code carried `sz.y - 1 - int(v_uv.y * sz.y)` in the accumulate and `1.0 - v_uv.y` in the present, because OpenGL row 0 is at NDC `-1`. Both are simply wrong here.
      - **The symptom was *stripes*, not a mirror, and that is why it took a readback rather than a code review.** A read and a write on different rows looks like a whole-image flip, and a whole-image flip is easy to reason about and easy to spot. It is not what happens: the write is wherever the rasteriser put the fragment and only the *read* is mirrored, so each row reads the row its mirror image reads. **A mirror is an involution**, so nothing smears and no frame beats — the history settles into holding `fresh(M^k(row))` for a column `k` frames old, which with `M² = id` means **alternate columns are the mirror of their neighbours**. At two pixels to the column that is a vertical stripe. Measured on a 256×128 target with a constant band profile, the *row means* came out symmetric about the horizontal centre — bright at both ends rather than in one quarter — which is the fingerprint, and it is the one shape a reader would describe as "the whole picture is mirrored" and therefore look straight past.
      - **`Trails` is immune for the structural reason it always was: its accumulate transform is a spin and a zoom about the pane's centre, so a whole-image `y` flip is one of that transform's own symmetries.** Only the waterfall carries per-column data, where a per-row flip is visible — so the pin is per-view for the same reason the memory keys are.
    - **`no_view_mirrors_the_pane_in_y` replaced `the_waterfalls_two_passes_flip_y_together`, which required the two passes to *agree* — and "agree" passes under either convention, so it could not have caught this.** The new one asserts the convention itself (neither pass flips), and its premise simulates a **column** per frame rather than a single row vector, because columns are where the striping lives: it checks that the round trip is the identity *and* that the settled target's stale columns are all-or-nothing mirrored. Mutation-checked on both passes.
    - **A fresh target is cleared to black, and a waterfall's silence is the background colour.** The present pass floors at `u_bg` (the same `mix` `Trails` uses), so an unwarmed history reads as the surface it is drawn on rather than as a hole in it.
- **The scroll is one column per frame, which makes the waterfall's duration in seconds frame-rate dependent** — 256 columns is 4.3 s at 60 fps and 8.5 s at 30. That was already true of the `VecDeque` version and is deliberately not changed: scrolling by `dt` would stop the column count being a fixed-width history, which is a larger change to what the view means than the wart is worth. `Trails` is the view where the time-based version matters, and it is time-based.
- **Flame** — three **tongues**, not a ridgeline, and that is the whole difference between this and a wave. The first shader version was a contour across the pane, which is the *silhouette of a wave*: it read as a wave because that is what it was, and the name had been doing work the drawing was not. What separates a flame is vertical — it stands on a floor, it comes to a point, it is hottest where the fuel is and cools toward the tips, and it licks sideways with the draught. So each tongue is a **Gaussian** in x (rounded shoulders, a pointed tip; the exponent is what sharpens the point), sheared sideways by an amount that grows with height, and flickering on its own phase so the *shape* changes rather than the scale. Three of them, each driven by a different part of the spectrum, plus a dim bed along the floor for them to stand on. The band array still supplies the heights, so it is still a music visualisation — it just no longer looks like its own name.
- **The VU meter is gone**, and the reason is worth having on the record. It was the only view on `compute_level`, and `loudness` is a real property a music visualisation is defined to follow — so this is a loss, not a correction. What made it go: it was the one view whose *state* was the point. A peak hold is a max over time then a linear decay, so the decay needs to survive between frames, which on a GPU is a feedback target and a second pass **to hold up one needle**, and its `db_scale` ended up as a second hand-copied implementation of a Rust function that no test could compare against. It also needed two palette tokens of its own (`u_slider_track`, `u_border`) and a third uniform (`u_hold`) that existed only for it. Three inputs, a mirror, and a feedback pair for a bar with a tick on it. The deletion took all three uniforms with it, so the block is smaller than it was.
- **Chladni** — a cymatic standing-wave figure, and the one view that is not a re-projection of the spectrum. The band levels become the mode numbers `(n, m)` (taken from the band array rather than a second FFT: a log-spaced band index is a good enough mode number, and a second transform per frame buys precision nothing here displays). What is drawn is the **nodal set** — sand collects where the field is at rest — and it is a **contour**, not per-cell marks. Three things make it one, and each was a bug first:
  - **The mode numbers are read *continuously* off the band levels, and that is the whole design.** `mode_now` in `audio/viz.rs` takes the weighted **barycentre** of each of two band groups, mapped into the resolvable mode range, and follows it over a time constant. It is the *only* channel the music has into the picture, and it is continuous by construction, so the plate follows the music on every frame instead of between switches.
    - **It replaced a hysteretic argmax, and the argmax was the defect.** The pick was `pick_mode`: the two loudest band indices, kept unless a challenger was `MARGIN_DB` louder on the pair's *weaker* band, then pinned for `HOLD_SECS`. All of that existed because a **discrete** pick has discrete failure modes — a bare top-two switched 60 times in 15 s over a drifting bass line, four whole-plate redraws a second — and the margin and the hold were the price of paying for that. But the price was the picture: the hold capped the figure at one change per 1.5 s **by construction**, so the image was bit-identical between switches. Measured: a hard 0.67/s even with two bands deliberately duelling at 8 Hz. Reported as "the chladni viz is rendering at 5fps", and — once that turned out to be a still image rather than a slow one — as "kinda still and unrelated to the music". **Neither symptom was a drawing problem.** The field is continuous in both mode numbers, so any real `(n, m)` is a valid cymatic figure, and a continuous read needs no margin, no hold and no anti-strobe machinery at all. `MARGIN_DB`, `HOLD_SECS`, `hold_tick`, `pick_mode` and the stored slide are all **deleted**, and `tplay.viz.chladni.mode` now holds one pair of floats whose only other job is to be held on silence.
    - **Two disjoint band groups, each mapped onto its own half of the mode range, so the degenerate `n == m` figure is structurally unreachable.** `n == m` cancels the field to nothing, so the plate goes blank. Two barycentres over *overlapping* ranges would need a check, and the check is one more thing to get wrong; disjoint groups mapped onto disjoint halves make `m - n` a difference of two quantities that cannot coincide. The old guard was a comparison in the view that could not fire (it compared two band *indices* from `enumerate`, distinct by construction), and `pick_mode` was the first place the invariant was observable at all — now nothing needs to be observable because nothing can violate it.
    - **The whole spectrum reaches the plate, and that was a second, separate bug.** Reported as "the nodes still move too little and are unrelated to the song" — and the second half of it was literal. `MAX_MODE` bounds the **mode** number (how many nodal lines fit on a plate) and it was *also* being used as the highest readable **band**. Those are unrelated quantities, and conflating them was catastrophic: the bands are **log-spaced over 20 Hz .. 22 kHz, so band 10 is 222 Hz**. Capping the band index at 10 left the figure seeing **25 Hz .. 222 Hz — 1% of the spectrum**. Every vocal, melody, snare and cymbal did *nothing at all*: a peak at band 2 (bass) and a peak at band 20 (1.6–2 kHz) produced **identical** mode pairs. It was a bass-only meter wearing a cymatic figure, and no continuity or range test could see it — both were true while two thirds of the spectrum was being thrown away.
      - `mode_now` now reads bands `1..VIZ_BANDS` and maps each group affinely into `1..=MAX_MODE`, so the cap bounds the **drawing** and the whole spectrum reaches it. A peak at band 30 (14–17 kHz) now drives the high mode number to its top.
      - **`MAX_MODE` is a drawing bound and must never be used as a band bound again.** That sentence is the whole regression guard, and `the_whole_spectrum_reaches_the_plate` is the test: a tone in each quarter of the spectrum, asserting the figure moves for each. A *range* assertion cannot catch this — the modes were always in range, they were just computed from the wrong input.
      - **The affine remap is where a real bug was caught.** `SPLIT + 1 + along * (MAX_MODE - SPLIT)` lands on `MAX_MODE + 1`; the high range is `SPLIT+1 ..= MAX_MODE`, so the span is `MAX_MODE - SPLIT - 1`. The range sweep found it as an out-of-range mode number on the first run.
    - **`MODE_POWER` is the responsiveness dial, and the reason it exists is that a barycentre of a bass-heavy spectrum is anchored.** Measured on the committed `lena.mp3`: **93% of its energy sits below 741 Hz**, so an energy-weighted centroid barely moves — the low group's barycentre wandered a fifth of its range no matter what the music did. That is not an arithmetic bug, it is what a centroid *is*, and it is the first half of "the nodes move too little". Raising the level to a power walks the read from centroid towards **soft argmax**, so the loudest band dominates and the figure follows the peak. Combined travel of the two mode numbers over the 12 s fixture, swept: `power 1/2/3/4/6/8/12/16 → 3.05 / 3.20 / 3.45 / 3.68 / 4.03 / 4.24 / 4.43 / 4.49` modes. **8, and the tail is why**: past it there is under 5% left to gain for a read that is by then very nearly the *old discrete pick*. The read is continuous in *level* at any power, so the handover property is unaffected; what grows is how much of the movement is a band changing places rather than the music's shape. A gain on the deviation from each group's centre was tried first and is worse in *both* directions — it exaggerates small wobble around the middle while pinning anything near an edge, so the figure spent its life clamped. Hence no gain constant: `MODE_POWER` is the only dial.
      - **There is a measured ceiling, and it is honest.** `n` saturates near 2.5 of its 4 modes whatever the power, because that is where the energy of real music actually lives. End to end through the real `draw` on the fixture, total travel is **5.09 modes** with the noise floor at **0.0007/frame** against music at **0.046/frame** — the motion is the music at roughly 65:1. `m` still travels less than `n`, because the energy above the divide is concentrated just above it; that is the spectrum reported faithfully rather than a clamp, and raising the divide measured *worse* (the high group's centroid span falls from 4.4 bands to 1.7 as it moves up).
    - **A barycentre is a ratio, so it needed a time constant — and the measurement is why.** A hundredth of a dB of FFT noise in one bin moves the read several times more than it moves that bin, and a high `MODE_POWER` widens that again. Unsmoothed, the read moved the plate by **0.046 of a mode per frame on a held sample** — no change in the music at all — against 0.064 for music that *was* changing. Two thirds of the motion was twinkle, which reads as a broken plate rather than a calm one, and is a worse failure than the frozen plate it replaced. One pole, `PLATE_TAU = 0.25 s`, dt-injected, and the same measurement becomes **0.0027/frame on a held sample against 0.0253 for the real recording** — the motion is the music at ~10:1, and the noise floor does not move at all where the music does. `PLATE_TAU` is a *time* constant and not a per-frame fraction for the reason `feedback_for_a_dt` exists; a degenerate `dt` **holds** the plate rather than snapping it to the target, the same direction `feedback_for_a_dt` takes, because a clock that cannot be trusted must not move anything.
    - **No `dt`-free overload and no second entry point**, so the clock cannot be left out at a call site: the smoothing is the reason the function is not a pure map of the bands, and a version without it is the version that measured as broken.
    - Pinned in `viz_tests.rs` by `the_whole_spectrum_reaches_the_plate` (a tone in each quarter of the spectrum moves the figure), `the_plate_moves_with_the_music` (energy traded up each group moves both modes, and by a *visible* amount — a read that shifted by 0.01 would be continuous and useless), `the_read_is_continuous_through_a_handover` (a band *level* rising past a fixed one, which is the exact point a discrete argmax is discontinuous by construction; a band *index* stepping would be a step-function input and a continuous function of it is allowed to step), `one_silent_half_still_moves_the_other` (a bass note with no treble above it is ordinary music), `silence_holds_the_figure`, `the_band_smoother_is_a_time_constant_and_not_a_frame_fraction`, `the_frame_clock_believes_a_frame_and_rejects_everything_else`, `the_read_cursor_turns_an_audio_burst_into_many_small_steps`, `the_read_cursor_stays_inside_the_ring_and_resets`, `a_second_read_in_a_frame_does_not_consume_the_arrival`, `the_read_cursors_advance_and_report_rules_are_stated_in_one_place`, `an_arrival_is_reported_once_and_only_while_audio_is_pushed`, `the_read_is_calmer_than_the_noise_it_is_fed` (an unchanging spectrum may not move the plate more than 0.1 of a mode in a frame — the floor real music has to beat), `the_pair_is_never_degenerate_and_stays_in_the_drawn_range` (every pair of peaks across the **whole** readable range × six level spreads — bounded by `MAX_MODE` it would have agreed with the bug) and `band_zero_is_never_a_mode_number`. A `settled` helper in the suite runs the read at 60 fps to convergence, because the read is *followed* and a single frame's value is a few percent of the way to the target — which is the point, and which no single-call assertion can see.
  - **The band smoothing is aimed at the spectrum, and it is now the only thing between the plate and FFT noise.** The plate's own read is followed over `PLATE_TAU` (above), and the band levels themselves are smoothed per view, so a transient cannot win the plate outright. **A view's figures are time constants** (`ATTACK_MS`/`RELEASE_MS`) rather than per-frame fractions, for the frame-rate reason in the `ATTACK_MS` bullet above; Chladni's pair is 46.7 ms attack / 18.2 ms release, the release slower than the plate's own follow so a band that stops being loud stops holding the figure.
  - **The line's width comes from `fwidth`, and that is the one thing a fixed field-space threshold could not do.** A fixed cutoff makes the stroke fat where the field is flat and hairline where it is steep, so the same figure would be drawn at two different weights. `fwidth(d) * 0.75` gives a 1.5px line at any mode and any pane size.
  - **`fwidth` is hoisted out of every branch, and the shader has none.** A derivative in non-uniform control flow is undefined — and a shader that `return`s early for the off-plate fragments never reaches the derivative at all, so "no early return" is load-bearing rather than stylistic. The off-plate test multiplies the colour out at the end instead.
  - **`n == m` is degenerate** (the two antisymmetric terms cancel, the figure is blank) and the field is antisymmetric, hence zero on the diagonal, which is where the mirror symmetry comes from. Those were four tests against a Rust `chladni_field`; the function is deleted and the formula lives in the shader. The *distinctness* guard used to be "enforced" by a view comparing two band **indices** from `enumerate`, which are distinct by construction, so it could never fire — the invariant was never observable there. `pick_mode` was the first place it became observable, and it is now **unreachable rather than tested**: `mode_now` reads two disjoint halves of the band range, so `n < m` holds by construction and there is no check left to get wrong.
  - **`Chladni3D` was a duplicate and is deleted, and the reason is the interesting part.** It claimed to march the field through a volume, but the field is a function of `(x, y)` alone, so all six of its z-slices returned the *identical* value and its `slab` was the arithmetic mean of six copies of one number — six times the work for a bit-identical picture. Once both views were per-fragment they were the same drawing with a glow on it, and a duplicate is a maintenance cost rather than a feature. The survivor is the good half of each: `fwidth` for the line's width (a fixed field-space cutoff draws one figure at two different weights), and the glow and edge fade from the volumetric one. `the_two_chladni_views_evaluate_the_same_field` went with the second copy — a mirror-drift guard for one copy is a test that asserts nothing.
- **Drawing: one fullscreen callback per view, palette colours only**, `scroll_bars = [false, false]` like the EQ pane. **No view adds a theme token**: the spectrogram's heat ramp is `mix(bg, accent, level)`, and every other view paints from the three tokens the harness already uploads.
- **Why this pane has no `fill_quads`, no `Mesh` and no convexity tests** — kept because the rule is the most expensive thing ever learned in this file, and a rewrite would otherwise rediscover it. `epaint::tessellator::fill_closed_path` has no ear-clipping and no scanline: it emits `for i in 2..n { add_triangle(i-1, 0, i) }`, a **fan from the first point**, so convexity is a *precondition*, and taking `PathShape`'s doc's "simple (non-self-intersecting)" for sufficient is how two views shipped broken fills. The second requirement is **feathering**: on by default at 1.0px, it *insets* the fill by half of that while feathering the rim outward, so adjacent shapes do not meet — and tiling one area from several `Shape::Path`s leaves a real ~1px unpainted gap along every shared edge, which survived a first fix that had addressed only the fan. The workaround was convex pieces in a hand-built `Mesh` (no inset and no feathered rim, so a shared edge is drawn once, by the two triangles meeting on it), plus a test group proving it. A fragment shader has no tessellator, so all of it is unnecessary rather than merely unused.
- No new dependencies — hand-rolled FFT and smoothing in `src/audio/viz.rs` (pure logic, covered by `tests/viz_tests.rs` without an audio device). The wgpu port **removed** two rather than adding any: `glow` and `egui_glow` were the GL backend, and `wgpu` is reached through `eframe::egui_wgpu`. The one dev-dependency is `wgpu` itself, and only so `tests/` can reach `wgpu::naga`.

## Album Cover
 
- Dockable pane (**Album Cover**), closed by default, auto-listed in the ☰ menu. Library `read_cover` helper plus the theme `nocover` placeholder icon — no new theme tokens, no new app state (the texture cache lives in egui memory).
- **Art source** (`library::read_cover`): the currently playing track's embedded tag picture (lofty `tag.pictures()`, first one), else a cover file beside the track (`folder.jpg`/`Folder.jpg`/`cover.jpg`/`Cover.jpg`/`folder.png`/`cover.png` — `COVER_FILES`, same house-constant style as `AUDIO_EXTENSIONS`). **A remote track resolves through `tracks::cover`**, which does the filesystem read internally: `read_cover` needs real bytes, and there is no file on disk named `smb://…`, so passing the URI directly always failed and the pane showed the placeholder. The pane never sees a resolved path at all. The pane's texture cache stays keyed by the URI, and no re-resolve case is needed: a remote track can only become *current* after being spooled, since playback uses the same cache. Reads on demand when the track changes — **not** part of the folder tag scan, so no MBs of art bytes in the background cache.
- **Decode**: `image::load_from_memory` (PNG+JPEG features) sniffs the format from magic bytes — no mime plumbing. Synchronous on the UI thread, one decode per track change (small, single-digit ms).
- **Cache**: egui memory under `tplay.cover` holds `(path, Option<TextureHandle>)` — keyed by the playing track's path, so a track with no art re-reads nothing until the track changes (the `None` half caches "checked, no art").
- **Drawing**: full-rect `ui.painter()`, `p.bg` fill like the Visualizer, art letterboxed centered with aspect ratio preserved; no art → the theme's `nocover.png` placeholder (128×128, panel_bg rounded square + text_secondary note, baked at generation; fallback chain: own → default theme → 🎵 glyph via `painter.text`), centered at pane-relative size. `scroll_bars = [false, false]` like the EQ/Visualizer panes.

## Library

- Filesystem browser (`TPlayApp::navigate_to`): the current folder's subfolders + audio files rendered as one combined row list (`library::Entry::Dir`/`File`). Subfolders are `📁` rows, audio files are tag-table rows. **There is no `..` row** — the breadcrumb is the only way up (it walks every ancestor and makes each non-last segment a jump target, so one level up is the second-to-last segment). Dot-prefixed (hidden) subfolders are skipped by default — a "Show hidden folders" checkbox in the ☰ menu toggles it (`app.library().show_hidden()` plus `set_show_hidden`, which re-lists on change; persisted by the config compare).
- **Header**: one breadcrumb widget (`gui/panes/library/header.rs`), drawn for **both** sources. `breadcrumb` renders whatever `Seg`s it is handed and holds no branch that knows about local paths or SMB URIs; the only per-source inputs are the two segment builders (`local_segs` walks the browsed dir's ancestors, `remote_segs` builds Local → host → share → each `rel` level) and `plan(n, always)`, which is the whole `…` rule. `always` is **how many leading segments are exempt from collapsing** and is load-bearing: 1 locally (just the filesystem root), **3 on a share** (`Local` / host / share), because those three are the way back out to a bigger scope — with `always = 1` for both, a deep share path loses its route to the share root, and with no `..` row that is a dead end. The share-list stage is 2 segments, so it sits under `always` and the "Local" exit can never collapse away. `Action` is an enum (not a closure, per the `dialogs.rs` rule) so `apply` stays one dispatch point neither builder has to duplicate; a segment's `hover` is `Some(full path)` locally and `None` on a share. All three pieces are pure and covered by `breadcrumb::*` in `gui_tests.rs` (mutation-checked). `remote_segs` filters the empty parts out of `browse.rel` because `"".split('/')` yields one: without that, a share root (`rel == ""`) produced a fourth segment labelled `""`, which `plan` then drew as the bold "you are here" crumb — a blank box at the level users sit at most. `a_share_root_has_no_empty_trailing_crumb` pins it, along with the level below it. The ★ favorite toggle is local-only, so it sits in `local_header` next to the breadcrumb rather than inside `breadcrumb`. **Placement is still per-source:** the local header is drawn above the sidebar (full pane width) and the remote one inside the main column, below the separator and level with the list. The "N tracks · M folders · K playlists" count and the **Add All** button are *not* here — they moved into `list_header_right`, drawn just above the list so the SMB share browser gets them too. The 4-column sortable header renders **only when the folder has audio files** — folders/playlists-only folders skip it (no tag columns to align to).
- **One file list, two sources** (`file_list_ui` in `gui/panes/library/listing.rs`): the search box, the sortable 4-column header, the folder/track/playlist rows and the "Scanning…" note are drawn once for `&[library::Entry]`. The local browser passes `library().entries()`; the share browser passes entries whose `path` is the file's `smb://` URI. That works because a URI is just a path whose last segment is the filename, so `title_or_stem`, `sort_key`, `is_playlist` and the search haystack all behave identically — which is what gives a share real tag columns, column sorting and search instead of the name+size list it started with. `parent_dir` used to draw the `..` row and is gone — the breadcrumb covers it (see the filesystem-browser bullet). Rows return an `Act` (`Nav`/`Play`/`Add`/`LoadPlaylist`) and each caller carries it out, since only it knows that `Nav` means `navigate_to` or `browse_open`, and that `LoadPlaylist` is synchronous locally but a spool-then-load on a share. `library::sort_entries` is the one sorter both use; descending is a `reverse()` after the ascending sort so ties don't reshuffle on every toggle.
- **Neither list virtualises, and the fix was two lines each because nothing else had to change.** A `ScrollArea::show` lays out and paints **every** row it is handed, scrolled out of sight or not, and a row is a dozen widgets and several text layouts — so a 2 000-track folder did all of that on every frame to draw the ~30 that fit. `row_visible(ui, row_h)` — in `gui/panes/mod.rs`, because the two lists are one rule and a copy is a rule that can be fixed in one place and not the other — compares the cursor against `ui.clip_rect()` and the row is skipped, **with its height still reserved** by `ui.allocate_space`: reserve nothing and the scrollbar collapses to the visible slice. One row of slack either side, so a partly visible row still draws — one row too many is free next to a row that should be there and is not. The Library checks it after the filter and before the draw; the Playlist checks it *before* the cache lookup and the title, since all three cost more than the comparison.
- **The row's position is `available_rect_before_wrap().min.y`, and it must never be `cursor().max.y` — writing that emptied the Library and the Playlist at once.** Inside a `ScrollArea::show` the content `Ui`'s cursor is `Pos2::INF` in its **min** corner (that is what "nothing placed yet" looks like), so `cursor().max.y` is `inf`, `top <= clip.max.y + row_h` is false for *every* row, and both panes silently painted nothing — on the first frame, on every frame, with no error. `available_rect_before_wrap()` reports the same position finitely, because egui derives it from the placer's rect rather than from a cursor that has not been set. **Three things hid it, and all three are now guards rather than luck.** (1) *The counts line read non-zero*, so the listing was provably fine and the eye went hunting for a data bug — the failure was entirely downstream of a correct `list_dir`. (2) *The existing pane test was blind by construction*: `the_playlist_pane_leaves_its_list_the_height_it_was_given` asserts `ui.min_rect()`, and the culled path still reserves each row's height, so the one test covering this code asserted exactly the property the bug preserved. **A `min_rect` assertion cannot catch a missing row, ever** — reserve nothing and the scrollbar collapses, which is the same reason the heights are reserved. (3) *A harness built on `allocate_new_ui` gives a finite cursor and passes with the bug present*, so the gate is only reachable by driving the real pane through a real `ScrollArea`; that is why `both_lists_emit_the_rows_that_fit` (`gui_tests.rs`) runs both panes through a real `DockArea` and counts **emitted banded rects**, with a premise of 40 rows per pane so neither bound can be satisfied by accident. It is mutation-checked on both halves — break the gate and it fails, **delete** the gate and it fails — and its lower bound is `> 1`, not `> 0`, because the Library's column header reuses `row_odd` for its background and is drawn whether or not the list works.
- **`file_list_ui` is a reader, and that is load-bearing rather than a style choice.** It needed `&mut TPlayApp` for exactly one call — `set_library_sort` from the header — and the caller had to hand it a slice of the folder's entries alongside, which is a `&` into the same `app`. So `local_list_ui` **cloned the entire entry list every frame**: a deep copy of every `PathBuf`, sixty times a second, to pass a slice to a function that only reads it. The one mutation is now `Act::Sort`, returned like every other action in that enum, so the caller can pass a borrow. The symptom was not a slow pane but **the whole application feeling laggy**, which is why four rounds of "the visualizer is slow" all pointed at the wrong file.
- **The SMB browser has the same shape of problem and it is not fixed.** `remote_list_ui` builds a `Vec<Entry>` with a `PathBuf::from(child_uri(...))` per row, **re-sorts it**, builds a second `Vec<PathBuf>` for the audio list and counts the untagged — every frame. A 300-file share does 300 URI formats, 600 path allocations and a sort per frame. The local list is fixed; this one wants the entries cached against the browse URI and the sort, which is a real change rather than two lines, so it is written down here instead of quietly becoming the next "very laggy" report.
- **`list_header_right` must use `Layout::right_to_left(Align::Min)` — the align token is load-bearing, not cosmetic.** A horizontal `with_layout` whose cross-axis align is `Center` or `Max` gives its child a `min_rect` spanning the parent's **whole remaining height** rather than the height actually used, and `Ui::scope_dyn` ends with `advance_cursor_after_rect(child.min_rect())` — so the parent cursor jumps by that whole span and `available_height()` collapses to 0. Measured in a 460px window against this pane's real shape: `Center` consumed **430px of a 444px column**, `Min` consumed the **21px** it used. With `Center` the list's ScrollArea was positioned at y≈497 — off the bottom of the pane — leaving only the Add All row visible beside the sidebar. **The damage scales with the parent's available height**, which is why it is invisible elsewhere: every other `with_layout` in the app sits under a *horizontal* parent (`coordinator.rs` top bar, `now_playing.rs` balance row, `playlist.rs` rows, `visualizer.rs` header), where the child's available height is one row; the one other vertical-parent site is `now_playing.rs`'s transport block, whose pane is ~15% of the window. Regression test: `right_to_left_center_does_not_swallow_the_column` in `gui_tests.rs` (premise-guards the trap, then asserts the geometry — that the list is still on screen, not the align token).
- **Playlist files as rows**: playlist files (see Playlist) are listed interleaved with the songs (`library::is_playlist` widens `list_dir`'s filter, and it matches `.tplay`/`.m3u`/`.m3u8`/`.pls` alike). A playlist row shows its full filename plus a "Playlist" tag right after the name (not floated to the far right), no tag cells and no `+`. Click → confirm (only if the current playlist has unsaved edits) → `load_playlist_from`, dumping the saved tracks into the Playlist pane for editing. Playlists are **not** tag-scanned (`navigate_to`/`library_scanning` exclude them, or "Scanning…" would stick) and **Add All** skips them — a playlist file isn't audio.
- **Places**: a fixed section above Favorites listing common user folders (`library::quick_folders` — Home + XDG Music/Downloads/Desktop, missing dirs skipped, dupes dropped). It is a free function in `library.rs` because it reads no app state, and the sidebar calls it **directly** — the one thing that used to need a `TPlayApp` delegate over it, which existed only for uniformity. Same row style as favorites without the ✕. (Volumes below does the same with `library::Volume::mounted_volumes`.)
- **Volumes**: local block partitions from `/proc/self/mounts` (`library::Volume::mounted_volumes`) — pretty disk labels win over UUID mountpoint names; click to jump (same row style as Places, no ✕).
- **Places and Volumes are read once per session, into egui memory under `LIB_PLACES`** (`SidebarDirs` in `sidebar.rs`). Both are pure functions of the filesystem, which is exactly why they were being re-read: drawing them inline cost `read_to_string("/proc/self/mounts")` plus a `read_dir("/dev/disk/by-label")` plus three `is_dir` probes — about six syscalls *per frame*, 60×/sec, for data that changes about never. A rescan happens on the next launch. The general rule this pins: **a per-frame draw must not call a filesystem reader** unless the answer can change within the session — that is the same reasoning as `is_ready` vs `local_file_in` over on the track side.
- **Network**: built-in SMB browsing (no mount). The sidebar's "+" opens a **host-only** add-server form (a bare host **or** a full `smb://host/share[/dir]` URI via `network::parse_server_input`, scheme optional): the host alone is saved and listed, while a named share drops straight into that share via `browse_open` — the GNOME-Files path that skips `list_shares` (IPC$ + srvsvc RPC) entirely, so servers that need it are still reachable. **Credentials are prompted for in the main pane, not the sidebar** (`login_form_ui`, rendered by `remote_list_ui` whenever the error is `LOGON_FAILURE`/`ACCESS_DENIED`), so a saved address is reused as-is and only the login is retyped. The prompt is keyed per host in egui memory (`(NET_LOGIN, host)`) and prefills the saved username; Connect calls `network_mut().add_server` (username is persisted) + `network_mut().set_password` (**password is session-memory only, never written to config**) and then retries **the stage it was on** (`browse_server`, or `browse_open` back into the share/dir) rather than bouncing out to the share list. A **blank username is not a guest account** — most NAS boxes reject it at SessionSetup, which is exactly what the prompt exists for. Cancel returns to the local browser (`leave_network`). Clicking a saved server swaps the main column for `remote_list_ui`: a breadcrumb (Local / host / share / dir segments — Local exits back to the folder browser), a "Connecting…" spinner or an error + hint line, then the **shared file list** — search box, sortable 4-column tag header, and folder/track/playlist rows — over entries whose `path` is each file's `smb://` URI (see **One file list, two sources**). Rows that are neither audio nor a playlist file are not listed, same as a local folder. `.` and `..` are dropped in `run_list_dir` (`network::is_self_or_parent`), because servers routinely include them and they are navigation artifacts, not content: they pass the `is_dir` filter, become real folder rows, inflate the "N folders" count, and produce a URI with a `.` segment the server rejects. This is **not** a hidden-file filter — a real `.config`-style folder stays reachable, because the share browser has no "show hidden" toggle to reveal it with, unlike the local browser's. This is a *different* `.`/`..` from the locally-drawn up-row that `file_list_ui` no longer has. At the share-list stage there is no directory, so the breadcrumb's "Local" plus a flat list of share names is all that's drawn. Add All, the composition counts and the search box all work here too, and add `smb://` URIs to the playlist unchanged. **Tags for a share are downloaded, not guessed** (see **Remote tags** below), so rows start as filenames and fill in — with a live count — as the files arrive. **Exactly one sidebar row is active at a time.** The server row highlights from `browse().host`, but the local rows (Places / Volumes / Favorites) must be gated on `!network_mode` — entering network mode does *not* change the browsed dir, so comparing against it directly left the last local folder lit *alongside* the server. That gate is computed once as `current_local: Option<PathBuf>` and compared by the three local rows. The reverse direction already worked: clicking a local folder calls `leave_network`, so the server row un-highlights. The server form state (`NET_FORM`) and remote browse state (`network::NetworkBrowse`) support the same click navigation as the folder browser. All network state (servers, session passwords, browse position, pending spool, in-flight tags, worker channels) lives in one `network::Network` object; the app exposes it via `TPlayApp::network()`/`network_mut()` and the GUI drives it **directly** — the one-line app wrappers over it (`add_network_server`/`remove_network_server`, `set_network_password`, `fetch_remote_playlist`) are all gone, since persisting `servers` is the config compare's job and not a setter's.
  - **A share row's `path` is a full URI, never a bare name** — the single most bug-prone thing in this pane, and it shipped broken once. `remote_list_ui` builds entries with `path: child_uri(&dir, &e.name)`, so `Act::Nav` arrives carrying `smb://nas/media/music/Rock`. **Split it** (`split_uri` → `browse_open(uri, share, rel)`, a no-op round trip); never feed it to anything that appends a name. Doing that produced a `rel` of `music/smb://nas/media/music/Rock` and a **PATH_NOT_FOUND** from the server. The `child_browse(host, share, rel, name)` helper that invited the mistake — four loosely-typed positional args where a URI in the `name` slot compiles fine and only fails server-side — has been **deleted**; `child_uri(parent, name)` is the only way to build a child URI, and its argument types make the confusion impossible. Guarded by `nav_uri_round_trips_but_renaming_one_does_not`, which asserts both that splitting round-trips exactly and that the wrong construction is detectably different. The one deliberate exception is the share-list stage, whose rows are built from `RemoteEntry::name` and so really are bare names — it is the only place that calls `share_uri` directly, and its variable is named `share_name` for exactly this reason.
- **Remote tags** — how a share's rows get titles, and why it downloads the files. `ensure_tags` splits its missing set: local paths to the `scan_files` thread, `smb://` URIs to `Network::fetch_tags`, which batches by host (credentials are per-command, so a playlist mixing two NAS boxes must not send one box's password to the other) and sends `SmbCmd::Tags` → `run_tags`. **`run_tags` spools the WHOLE file and reads tags from the cache copy** via `run_spool` + `library::read_info`. That is deliberate, and it replaced a header-prefix read that could not deliver parity:
  - A prefix cannot serve every format. WAV needs its complete `data` chunk; M4A's `moov` atom usually sits at the end; FLAC and MP3 tag blocks vary in size. Measured against a real share: FLAC never tagged, and MP3 tagged only sometimes — "some worked, some only loaded when played", which is the signature of a tag block falling outside the prefix.
  - A prefix cannot give a true **duration** either. lofty derives duration from the bytes it is handed, so a 64 KB prefix of a 7.8 s track reported **4.1 s** — silently wrong, which is worse than absent.
  - The download is not wasted: `run_spool` writes into the same cache playback reads, so playing the track afterwards is a cache hit, and an already-cached file skips the network entirely.
  - The trade is bandwidth and disk for correctness: browsing a 300-file share downloads it. That is the only way a remote row can match a local one, which is the stated goal. The share browser shows a live count (`Network::pending_tags`) so the wait reads as progress.
  - Results arrive as `Event::Tagged(Vec<(uri, Result<TrackInfo, String>)>)` and land in the **same `tag_cache`**, keyed by URI, so every pane fills in with no UI work. **`Ok` is cached even when every field is blank** — that is the definitive "read it, it has no tags" answer, and `title_or_stem` falls back to the stem on an empty title, so it displays exactly like no cache entry. **`Err` is NOT cached**: a failed transfer says nothing about the file's tags, so caching it would blank the row for the rest of the session. Leaving it out is what makes it retryable.
- **Two separate tag counters, and why** (`network.rs`): `tagging: HashSet<String>` is what is **in flight** — it is what `busy()` reads (so `request_repaint` keeps coming) and what `pending_tags()` counts for the progress line. `tag_attempts: HashMap<String, u8>` counts **failures**, cleared on success, and a track that reaches `TAG_ATTEMPTS_MAX` is not asked again this session. They must not be merged: the browser asks for every uncached track *every frame*, so an unbounded retry re-queues a dead server 60×/second forever, while a retained failure mark inside the in-flight set would pin `busy()` true and spin the event loop forever. Both directions are guarded by `tag_attempts_are_bounded_and_cleared_on_success`.
- **Spool cache eviction** — the cache has no TTL and no other reason to shrink, and tagging now fills it. `Config::spool_cache_mb` (default 2048, i.e. 2 GiB, hand-editable in `config.json` and written back by `flush_config` so a hand-set value survives) is the ceiling. `Network::evict_unplayed` runs after a tag batch lands — not per frame, since it walks the directory — and deletes via the pure, testable `select_evictions`: **largest unmarked first, never a played file**. `Network::mark_played` is called from inside `Network::spool` itself — a user-requested spool is one they asked to *hear*, so it is exempt from the moment they ask, including while the download is still in flight. The failure mode is therefore a re-download, never a broken play. Unmarked-ness is session state: after a restart every file looks unplayed and is therefore evictable, which is the safe direction.
  - **Everything is keyed by the file's *stem*, never `file_name()`.** The on-disk name is `<spool_key>.<ext>` (`cache_path_in`) while `spool_key` and `mark_played` use the extensionless key, so the stem is the only value the two sides agree on. Keying the entries on `file_name()` while deleting by `file_stem()` made `select_evictions` pick the right files and the delete match none of them — the ceiling silently never applied and the cache grew unbounded. `CacheEntry` therefore also carries `path`, so a selected key needs no second directory walk, and the whole thing runs through `evict_unplayed_in(dir, budget)`: a *pure* `select_evictions` can only prove the policy, never that a key resolves to a file, so the wiring needs its own test (`evict_unplayed_in_deletes_what_it_selects`).
  - An in-flight file is never a candidate in practice: the worker is sequential, so at most one spool is open, and a whole-file `fs::write` entry is the smallest and therefore evicted last.
- **Favorites** ★ toggles the current folder; persisted with the last browsed dir to `~/.config/tplay/config.json` (`{library: {favorites, last_dir, show_hidden}}`), restored on startup. Places, Volumes and Favorites are the **same row** with different data, so they go through one `sidebar_row` helper in `gui/panes/library/sidebar.rs` (label + accent-when-current + optional ✕, reporting `RowClick::Jump`/`Remove` for the caller to carry out — the ✕ means "unbookmark" on a Favorite and "forget server" on a server row, so only the caller knows). The row width is `ROW_W`; the server rows keep their own `SERVER_ROW_W` and their own hover, being a different row. The Places/Favorites column is a **fixed 120px** (`SIDEBAR_W`, fits the 320px minimum window alongside the file list) and scrolls vertically when the stack outgrows the pane. It is allocated as an exact rect via `ui.allocate_space` + `ui.new_child` — *not* `ui.vertical` + `set_min_width`, and *not* a bare `new_child` (see the three egui traps under `gui_tests.rs`). The **add-server form is wrapped the same way inside the scroll content** — without that, the TextEdit overflow kept growing `content_size.x` and dragged the sidebar's scrollbar around. Its ScrollArea carries `id_salt("places_favorites")` (sibling-column uis resolve to the same stable `ui.id`, so a plain `ScrollArea::vertical()` would clash with the file list's and trigger egui's ID-collision overlay) and `auto_shrink([true, false])` so it follows its content's width *within* the fixed column instead of claiming the whole row and squeezing the file list to nothing.
- Each file row is a fixed-column table: track-no title (flexible), then Artist/Album/Duration cells mirroring the header, with a `+` button — all from the **background tag scan** — `library::scan_files` (a thread per scan) tag-reads every file with `lofty` (ID3v2 / Vorbis comments / MP4 ilst / RIFF INFO) and sends `(path, TrackInfo)` over an mpsc channel that `TPlayApp::update()` drains into the shared `tag_cache` each frame. Revisits are instant (cache check skips the scan); filenames stand in until the scan lands; a "Scanning…" label shows while any current-folder file is missing from the cache.
- **The star rating is a file tag, not app state.** `TrackInfo::rating` is `0`–`5`, read by `read_info` from the file's Popularimeter — lofty 0.25 exposes it typed, as `Tag::ratings()` (`POPM` for ID3v2, `RATING` for Vorbis/RIFF, `rate` for MP4 ilst) — so it survives a re-scan and every other player sees it. **The write side is the asymmetric half**: `TagItem` values are text, so writing a rating is `insert_text(ItemKey::Popularimeter, Popularimeter::musicbee(r, plays).to_string())` against the public `musicbee`/`picard`/`windows_media_player` constructors. Two ceilings, both real: a `StarRating` holds **whole** stars only, and lofty routes a foreign POPM scale through a provider (`128` from an unrecognised email becomes 3), so a half-star library arrives rounded. `ratings()` drops what it cannot parse, so a malformed frame reads as *unrated* rather than failing the scan — pinned by `a_stars_rating_written_to_the_file_reads_back`, which also asserts the rewrite kept the other tags (lofty rewrites the tag block rather than appending, and that fixture is what the whole remote-tag path is verified against).
- **The rating cell opens the track editor**, which carries the four text tags as well as the stars — so the cell's job is the *fast* half of an edit, and the modal is the whole one. The cell is one compact cell, not five clickable stars. `RATING_W` (24) + `RATING_STAR` (10), after the Duration column and outside `CELL_WIDTHS` — those are the *sortable* columns, and the header draws one cell per `SORT_OPTIONS` entry and stops, so a cell past the last header one still lines up. Five stars would be ~55px on a row whose `ROW_FIXED_W` is already 274, collapsing the title column much earlier. The star carries "is it rated" (`star_on`/`star_off`, baked accent vs secondary per theme, so it needs **no tint**) and the digit carries "how much", because a filled-vs-empty star cannot tell 1 from 5. Clicking it arms the editor; the **play count rides on hover** (`TPlayApp::play_history` → `PlayStats::describe`) rather than in a counter column nobody asked for. It is deliberately **not sortable**: a whole-star field would order into long runs of indistinguishable rows.
- **The rating is display-only on a share, and that is two layers.** `file_list_ui` drops a `FileAct::Edit` when `remote` is set — a spool-cache copy is not the track — and `tracks::write_tags` refuses an `smb://` id independently, so a caller that forgets the GUI guard still cannot write to a cache. **Why the write lives in `tracks.rs` and not `app.rs`:** this is the third `is_remote` site the module rules allow, and it is the same kind of question as the other two (a playlist moving to and from a share) — about *path semantics*, not track identity. It also means the GUI never asks, so "no `is_remote` in `src/gui/`" stays absolute.
- **A write that fails must be visible.** `apply_edit` returns `Result` and touches nothing on `Err` — the file, the cache and the sort order agree or the call did nothing, because a half-applied edit is worse than a refused one. The editor keeps its modal open with the error on it, since a tag that silently did not change is the failure mode worth designing against. Two lofty facts shaped `write_tags` and are worth knowing before touching it: `tag_support` is **optimistic** (it reports ID3v2 as writable for a WAV, which the RIFF writer then refuses), and `insert_tag` returns the tag it *replaced*, so its result cannot distinguish a refusal from a success — the only honest check is what the file then carries. Hence the candidate loop, and hence the untagged-WAV test.
- **Smart Views** — a saved rule query, evaluated against the database and rendered as a playlist. A **section in the Library sidebar**, above Favorites: the same `sidebar_row` shape, with the ✕ forgetting the view rather than un-bookmarking a folder, and a `+` opening a popup of `library_db::presets()` — a **popup rather than a form or ComboBox** because the preset labels are longer than the 120px column and a popup draws outside it, so nothing there can widen the sidebar (see the `allocate_space` note above) and no egui-memory key is needed for an open/closed flag. Clicking a view replaces the playlist through the **same tail as a `.tplay` load** (`apply_playlist`), with the dirty-playlist confirm in front of it — the identical gate a playlist row uses — and with **no tracked file**, so Save asks where to go exactly as it does for a new playlist.
  - **`Rule` is a struct of optional `Option`s, AND-ed, and that is not a stylistic choice.** It is *more* expressive ("rated 4+ **and** played 3+" is one rule, not a new variant) and it is **forward compatible**: `#[serde(default)]` on the struct means a `library.json` written by a build carrying a constraint this one has never heard of still loads, where a serde enum fails on the unknown variant — and that failure costs the whole file, play history included. A new constraint is one field on `Rule` plus one line in `presets()`; the popup needs no new branch, because a preset is data that *writes* a `Rule`.
  - **An empty rule matches nothing, not everything.** The alternative — "no constraints, so everything" — means a view whose one constraint was dropped from its definition silently becomes the whole library, and the next click replaces the playlist with all of it. Pinned by `an_empty_rule_matches_nothing_rather_than_everything`.
  - **`top_played` is a ranking, not a filter**, and it is the one constraint that changes the *order*: everything else comes back in the library's own order (`sort_key` on the title column, the same default the file list uses), ties broken on the track id because a `HashMap`'s iteration order is per-process random and a view that reshuffled on every launch would reorder the playlist each time it was clicked. It also never pads to its limit with tracks nobody has played, and `added_within_days` treats a never-persisted track as **not matching** — it has no first-seen, so it is new rather than old, and claiming it either way would be a guess.
  - **A view is identified by its name**, so `add_view` *replaces* a same-named one: two sidebar rows reading "Unrated" would make the second undeletable in practice.
  - **What a view can see is what the tag cache holds** — the folders browsed so far, in this session or a previous one. There is no indexer, so "top 25 played" is over *that*, which is the honest ceiling — the day it stops being is the day the scan stops being the thing that knows the library.
- **Sortable header**: the file list has a clickable column header (Title / Artist / Album / Duration) above the ScrollArea — one column per row cell (no separate Name column). Click picks that column ascending; clicking the active column flips direction (`TPlayApp::set_library_sort` → `apply_library_sort`, comparator `library::sort_key` keyed by `SORT_OPTIONS` index). **Folders participate**: they're untagged entries, so Title sorts them by their own name (interleaved with files) and the tag columns sink them below the files. `sort_key`'s last arm falls back to the filename, which is right for a column nobody knows and wrong for a *fifth real* one — adding a column to `SORT_OPTIONS` compiles, passes every test, and silently orders it by filename. `SORT_OPTIONS` has gained and lost entries before (Year and Genre were removed), so a `debug_assert!(col >= SORT_OPTIONS.len())` sits in that arm: it fires when a column inside `SORT_OPTIONS` got no arm. It has nothing to assert today, which is the guard working, so the test pins the *other* half instead — an out-of-range column must still fall back rather than trip the assert, since turning a wrong order into a debug panic is the worse bug. The active column shows a theme sort icon (accent-colored per theme: `sort_asc`/`sort_desc` — generating these was the fix for the old ▾/▴ glyphs, which are tofu in every bundled egui font) and accent color. Untagged fields sort last (empty strings, missing durations).
- **The Album column is album + track number, not album alone** — the sort key is a composite `"{album}\x01{track:06}"`, so one album lists 1, 2, 3… rather than alphabetically. `track_no` is lofty's raw `TrackNumber` string, parsed as a number; the zero-pad is what makes 2 precede 10 (a plain string sort gets that backwards). **Unnumbered tracks fall back to the title in that slot**, so they group alphabetically *after* the numbered ones (`'0' < '1'` is the ordering, not a coincidence) and a `"3/12"` multi-disc number — which does not parse — still groups by album but orders by title. An empty album takes the `\x7f` prefix so an untagged file ties with a folder in the sink region instead of sorting above every album. `ponytail:` parse the leading digits if multi-disc ordering ever matters. Year and Genre were **removed** from `SORT_OPTIONS` and `TrackInfo` (nothing read them once the columns went).
- **Sort key encoding** (`library::sort_key`): returns a lowercase string for case-insensitive sorting; empty/missing values get a `\x7f` (DEL) prefix so they sort after normal content; durations become zero-padded milliseconds. Folders are untagged (empty strings → sink last on tag columns).
- Click a song row → `play_file` — a **direct open**: `current_index = None`, the playlist's sequential flow and shuffle state are untouched, and auto-advance won't cascade off it. The `+` row button and the **Add All** header button add tracks to the current playlist via the existing `add_files` dedup.
- Search box filters the current folder's rows by title/artist/album, with the stem as the title's fallback. The matching is `library::entry_matches` — `pub` and `Ui`-free, extracted for the same reason `playlist::row_matches` is: the filter runs for every row of every folder on *both* browsers, so it is the hot path and the one piece of this pane no windowless test could reach. Its empty-query short-circuit is the first statement for a measured reason: above it, an unfiltered 500-file folder formatted a haystack per row per frame and discarded all of them. **It searches the tags, not the filename**, which is a real difference from the Playlist box (that one also searches the filename) and is asserted rather than accidental — see the `entry_matches` row in **Key constants**.
- Row styling reuses the playlist pattern: `--row-even/odd` banding, 3px accent stripe + tint on the currently playing row. Folder rows paint the per-theme `folder` icon (tinted from `text_secondary`, baked at generation); the favorite toggle uses `star_on`/`star_off` (accent/secondary); the per-favorite remove row button and the sort direction are theme icons too. Glyph fallbacks must exist in the bundled egui font stack (Ubuntu-Light / NotoEmoji / emoji-icon-font) or they tofu.
- **Per-session init flag**: `tplay.library.init` in egui memory ensures `navigate_to` runs once on the first frame.

## Themes (data-driven, dark / retro / neon)

- All colors flow from each theme's JSON `Palette` tokens mirroring the reference CSS custom properties. Panes paint rows/labels/metadata straight from tokens via the `&ThemeState` they are handed (`themes.current().palette`, `themes.current().metadata_font`) — the theme is GUI state, so it arrives as a parameter, not through the app.
- Token → egui `Visuals` mapping (see docs on `theme::apply`): `--bg` → panel/window fill, `--text-primary` → `override_text_color`, `--progress-fill` → `selection.bg_fill` (the slider's trailing fill), `--slider-track` → `inactive.bg_fill` (rail), `--slider-handle` → `inactive.fg_stroke` (knob), `--focus-ring` → `selection.stroke`, `--accent` → hyperlink/active fill. `--row-even/odd` and `--text-secondary` can't be expressed in Visuals — panes use them directly.
- Theme files are plain JSON + SVG — creating/modifying a theme is drop-in editing, no rebuild. Theme selection persists in `~/.config/tplay/config.json`; config absence or unknown id = `dark`.
- Icons: `themes/<id>/icons/<name>.svg` (23 fixed names, one per `Icon` variant). Resolution: own file → default theme's file → glyph. Rasterized synchronously into `egui::TextureHandle`s (one per `Icon::ALL` slot) at startup and on a switch (`ThemeState::set`, called by the ☰ menu with the `Context` it already has); `themes.icon(Icon)` hands them to `theme::icon_button`/`theme::icon`. **`Icon` and its `DATA` table are append-only**: `index()` is the enum discriminant and `DATA` is indexed by it, so a new variant goes at the end of the enum *and* the end of both `ALL` and `DATA` — put it anywhere else and every later icon decodes the wrong file. **16 of the 23 are [game-icons.net](https://game-icons.net) artwork under CC BY 3.0 and 7 are original to this repo** — `logo`, `stop`, `shuffle`, `gapless`, `crossfade`, `new_list` and `nocover`; per-icon attribution and the re-derive URL are in `CREDITS`.
  - **The SVGs are the source of truth, one set per theme, colour baked in.** Each file's `fill` carries that theme's own palette token, which is what lets a theme ship a set nobody else has — and the cost is that the colour now lives in 23 files instead of one, which is exactly what `themes/recolor_icons.py` pays back. There is no runtime tinting and no intermediate PNG: `theme::rasterize_icon` renders the SVG straight to a texture. A theme that ships no icon of its own falls back to the default theme's files, so **a new theme needs no icons at all** to render. A glyph is only ever painted when neither the theme nor the default ships the file, and several glyphs are known to tofu in the bundled egui font — which is exactly why the files exist.
  - **`logo` is the one exception, and it is not a themed glyph.** It is the app's own full-colour mark — a bolt over a play triangle on a rounded plate — so there is no palette token behind it: the three per-theme copies it replaced were byte-identical, and flattening it to one token would delete the artwork rather than recolour it. It therefore lives **only** in the default theme (`themes/dark/icons/logo.svg`) and retro/neon reach it through the same fallback as any other icon, and `recolor_icons.py` skips it via `FIXED` rather than reporting it as a slot with no token — a missing row already leaves a file alone, so `FIXED` buys the **exit code**, not the bytes. Its shading is **one `linearGradient` per shape** in a `<defs>` block rather than a single baked `fill`, and that is invisible to the recolour twice over: the regex matches `fill="#rrggbb"` and `stroke="#rrggbb"`, so neither `fill="url(#…)"` nor `stop-color` can be rewritten.
  - **`rasterize_icon` supersamples 4× and box-averages, on premultiplied RGBA.** resvg already antialiases, but a 20px glyph straight off a 512 viewBox is a hard minification, and the supersample is what keeps a 1px diagonal stroke from aliasing into dashes. Premultiplied is the only correct order to average in where a pixel is partly covered — averaging straight alpha darkens every antialiased edge — and `from_rgba_premultiplied` then hands egui exactly that, so nothing is unpremultiplied on the way out. The scale comes from **the tree's own size**, not a hardcoded 512: the game-icons files are `viewBox="0 0 512 512"` and the hand-authored ones `0 0 20 20`, and both still have to land on the same output size.
  - **`Icon::px()` is 20 for every slot except `nocover` at 128**, and it cannot be one constant: rendering everything at 128 and letting `TextureOptions::LINEAR` minify 6.4× down to a 20px button shimmers on thin strokes, because there is no mip chain to pre-filter it. The 128 is the Album Cover pane's placeholder, which is painted at pane size and so has to be rasterized large to stay crisp.
  - **The upstream background rectangle is load-bearing to remove.** Every game-icons file is `<path d="M0 0h512v512H0z"/>` (opaque black) plus the glyph in `fill="#fff"`, so a file that kept it rasterizes to a solid black square. `every_icon_has_a_parseable_svg_source` in `gui_tests.rs` asserts each file has both an opaque *and* a transparent pixel, which is what catches that — "it parsed" is not sufficient, since a fully-opaque and a fully-transparent file both load without error and both render as a solid block. That test replaced `every_bundled_theme_decodes_the_generated_icons` and covers both directions the deleted `generate_icons.py --check` used to: it proves every slot's file parses **and** rasterizes, and `no_icon_file_is_without_a_slot` is the "file with no slot behind it" direction, which nothing in the app could see.
- Retro: light Winamp grays + blue (`accent`/`progress_fill`/`focus_ring` = `#15449e`, a darker royal blue than the original — measured to keep accent-as-text ≥ 4.5:1 on the light surfaces), `metadata_font: monospace` for times/metadata (monospace digits are tabular — the seek-bar time labels can't jitter in retro). Neon: near-black blue + mint accent/pink progress.
- **Layout tokens**: each theme may include a `layout` object with EQ sizing values (`eq_slider_min_h`, `eq_slider_max_h`, `eq_band_w_min`, `eq_header_gap`, `eq_band_gap`), the type scale (`text_meta` 12px, `text_time` 13px — threaded through every pane's label/font sizes, no magic sizes in pane code), and the active-row tint alpha (`row_tint_alpha`, default 0.10). These drive the equalizer pane's minimum/maximum slider height, minimum band width (the dock floors the pane's width at `BANDS × eq_band_w_min` — `BANDS` being `EQ_FREQUENCIES.len()`, so 10 today; at the default 30 the floor (300px) fits inside the 320px minimum window since the band row clips below it — no scrollbars), spacing, and the row highlight, replacing hardcoded values. Defaults live in code (`Layout::with_defaults`), and they are applied **once**, by `Theme::from_json` — so `Theme::layout` is complete by construction and a pane reads `theme.layout` directly. Every pane used to re-run `with_defaults` per row per frame (three times per Library row), which was the same eight `if x > 0 { x } else { DEFAULT }` arms rebuilt 60×/sec for a value that could not have changed. If a new `Layout` field arrives, it goes in `with_defaults`'s one `or()` closure and in `from_json`'s one `num()` closure — two lines, not sixteen.
- **Active-row tint**: `theme::row` paints a *translucent* accent overlay (`row_tint_alpha` alpha) over the banded bg plus a 3px accent stripe — not `accent.gamma_multiply()`, which crushed to near-black and rendered the highlight invisible. The overlay keeps title text ≥ 9:1 in every theme (see `contrast_tests`).
- **No widget animations**: `theme::apply` sets `style.animation_time = 0.0` each frame, so a mid-session theme switch (and every hover/active transition) lands instantly — no color cross-fade smear. Winamp-snappy on purpose.
- **Theme JSON schema** — `id` and `palette` (13 tokens) are required; everything else has a default:
  ```json
  {
    "id": "dark",
    "name": "Dark",
    "base": "dark",
    "metadata_font": "proportional",
    "palette": { "bg": "#141414", "panel_bg": "#1d1d1d", "text_primary": "#e0e0e0", "text_secondary": "#8c8c8c", "accent": "#2ea3f0", "border": "#383838", "progress_fill": "#2ea3f0", "slider_track": "#2b2b2b", "slider_handle": "#9a9a9a", "row_even": "#171717", "row_odd": "#202020", "btn_hover": "#2a2a2a", "focus_ring": "#2ea3f0" },
    "layout": { "eq_slider_min_h": 60, "eq_slider_max_h": 220, "eq_band_w_min": 30, "eq_header_gap": 6, "eq_band_gap": 2, "text_meta": 12, "text_time": 13, "row_tint_alpha": 0.1 }
  ```

## Docking (egui_dock)

- Six panes as tabs: **Now Playing**, **Playlist**, **Equalizer**, **Library**, **Visualizer**, **Album Cover**
- **Pane sizing**: all panes are `Fill` — they take their dock share and resize via separator drag; `apply_min_pane_sizes` only *floors* every pane at its measured content size (Playlist/Equalizer/Library measure their bodies; Now Playing records its content height under `tplay.pane_content_h` and draws its controls **vertically centered** — the top pad is half of `available_height() - last frame's content height`, so it converges one frame after a resize). No pane is pinned. Minimum floors are enforced in one pass: `apply_min_pane_sizes` runs **after** `DockArea::show` — the only pass that can see the result, since the splitter drag and the floating-window resize both happen inside `show()` — and `ctx.request_repaint()` lands the corrected fractions next frame, so dragging below the EQ sliders' minimum height snaps back instead of sticking. Nothing floors a pane *before* its opening frame, which is the known gap.
- Default layout: top row (Now Playing tab) ~15%, bottom (Playlist) ~85%
- Drag tabs to reorder; drag onto split overlays to dock left/right/top/bottom/center
- Resize panes via draggable splitters
- Tear tabs off into floating windows
- **No tab bar paints a close button** — the ☰ menu is the only way to hide a pane. `egui_dock` 0.21 puts **two** ✕ controls on a tab bar and **every one of them defaults to `true`**: the one inside a tab (`show_close_buttons`) and the one at the right end of the bar (`show_leaf_close_all_buttons`). Each leaf holds exactly one pane, so the second reads as that pane's own close button, which is what a user reports seeing. Both are off in the `DockArea` chain, beside `show_leaf_collapse_buttons`. **`is_closeable -> false` is not a substitute for the second flag** — it *greys the close-all button out* rather than removing it. ## Playback niceties

Balance, elapsed/remaining, gapless and crossfade — four small playback features
that share one mechanism, so they are documented together. Each is a
`config::Prefs` field persisted in `config.json`; the mechanics are under
**Implementation notes** at the end of this section.

- **Balance (L/R)** — `balance: f32` (`Config`, default 0.0, range -1..1), read
  and written as `app.prefs().balance()` / `app.prefs_mut().set_balance(..)`.
  Live, no sink rebuild. Slider in the Now Playing pane, double-click to center.
  **rodio has no `Sink::set_pan`** (0.22 renamed the type `Player`; neither has
  the method), so it is a source wrapper
  (`BalanceSource`), not sink-level panning.
- **Elapsed ↔ remaining** — persisted `remaining: bool` (the `viz_view` pattern,
  via `Prefs`). The clickable elapsed/remaining label in Now Playing toggles the
  mode.
- **Gapless** — `gapless: bool`. Within `PREROLL_SECS` of track end the xf sink
  pre-buffers the next track at volume 0 and swaps on the current track's drain —
  zero gap, zero overlap, no queue fusion.
- **Crossfade** — `crossfade: bool` + `crossfade_secs: f32` (default 3, capped at
  `MAX_CROSSFADE_SECS`). A real two-sink crossfader: the outgoing track plays
  full-length while the incoming one plays simultaneously in a second sink on the
  same mixer, equal-power faded per frame. Each track is heard exactly once, no
  repeated tail, and it supersedes gapless when both are on. Duration slider in
  the menu.

### Implementation notes

**New source modules** (pure, headless-testable, mirror `audio/eq.rs` pattern):
- `src/audio/balance.rs` — `BalanceSource<S>` wraps any `Source<Item=f32>`,
  applies per-channel gains from `Arc<RwLock<f32>>`, outputs stereo.
  `balance_gains(f32) -> (f32,f32)` linear curve (center = 1.0/1.0 exact passthrough).
  Tests: `tests/balance_tests.rs` (8 tests, identical harness to `eq_live.rs`).

- `src/audio/transition.rs` — free functions `build_gapless_next()` (a full,
  buffered EQ → Tap → Balance source — the unit both sinks play),
  `fade_gains(p) -> (f32, f32)` (equal-power cos/sin crossfade curve),
  `xf_gains(remaining, crossfade, cf) -> (f32, f32)` (the fade *progression* —
  what p is computed from, which is the half that decides whether a track is
  audible or dropped; gapless returns `(1, 0)` so the caller has no branch), and
  `arm_plan(&ArmInput) -> Option<Armed>` (the pre-buffer decision).
  **Seek-first helper** `seek_or_skip()`: attempts `try_seek()` (fast path for
  FLAC/WAV/OGG/M4A) before falling back to `skip_duration()` (eager decode for
  unseekable streams). No UI code, pure logic. Tests:
  `tests/gapless_crossfade.rs`.
- **The arm is a decision, not a side effect** (`arm_plan`, added later — the one
  piece of this milestone that is *not* in `app.rs`). It was a 50-line block
  inside `TPlayApp::advance`, and its failure modes are silent (a skipped arm is
  a gap, a wrong arm is a silently skipped track), so nothing would ever have
  caught a regression in it. It now reads an `ArmInput` struct and returns
  `Option<Armed>`; `advance` keeps only the effects (build the source, make the
  sink, flip the metadata). What stayed in `advance`, and why:
  - **the sink-shape gate** — `!is_paused`, `len() == 1`, a current track and
    index, and the mode check. `Player` facts with no data equivalent, and the
    cheap outer gate. The mode check is duplicated by `arm_plan` on purpose:
    with both modes off this block would otherwise run — and peek — on every
    frame of every track for nothing.
  - **choosing the candidate** — `peek_next_index()`, because choosing cannot
    happen inside a pure `arm_plan` and, more importantly, must not happen on
    every frame. The arm re-evaluates until it resolves, so a *picking* call
    here rewrote the shuffle order 60 times a second. It peeks, and commits
    (`commit_next_index`) only once the arm actually lands — see **Shuffle
    order**. An earlier version picked up front and left the entry behind even
    when the arm was then skipped, which marked never-played tracks as played;
    that is fixed, not preserved.
  Every guard in `arm_plan` is pinned by a test in `gapless_crossfade.rs`; the
  suite is mutation-checked, so a loosened comparison there fails the build.

**App state additions** (`src/app.rs`; the `Config` half now lives in `config.rs`):
- `Config`: `balance`, `remaining`, `gapless`, `crossfade`, `crossfade_secs`.
- `TPlayApp` fields: `xf_sink: Option<Player>` (incoming track, second sink on the
  same mixer) and `xf_out_total: Option<Duration>` (the outgoing track's
  duration, captured at arm time — the arm flips `total_duration` to the
  incoming track for the seek bar, so the fade math needs the outgoing total
  saved separately). **The *fields* kept their old names** (`sink`, `xf_sink`)
  through rodio's 0.21→0.22 rename, which is deliberate: only the type moved,
  the concept did not, and renaming every field and every doc mention would be a
  large diff for no behaviour — so `Player`-typed fields named `sink` are
  expected, not an oversight. `balance`/`remaining`/`gapless`/`crossfade`/
  `crossfade_secs` were five flat fields here once; they are `config::Prefs` now.
- Accessors: all six live in `config::Prefs`, reached as `app.prefs()` /
  `app.prefs_mut()` — `balance()`, `remaining()`, `gapless()`, `crossfade()`,
  `crossfade_secs()`, `viz_view()`. (They were once 12 app-level delegates; see
  **Appwide settings**.)

**UI additions** (`src/gui/panes/now_playing.rs`, `src/gui/coordinator.rs`):
- Now Playing: new second row under transport controls — Balance slider with "Balance" meta label (left-aligned, double-click resets to center 0.0) + Gapless/Crossfade **icon buttons** (18px, lit via `selected()` visual, same convention as lit shuffle/repeat icons).
- Volume slider now stands alone in the transport row (no balance crowding).
- ☰ menu: "Crossfade" section (constant height) — crossfade duration slider **always visible and editable** (no `ui.add_enabled` guard), Gapless/Crossfade checkboxes removed (now icon buttons in Now Playing row).
- Icon set gained `gapless.svg` + `crossfade.svg` here (text_primary baked per theme, glyph fallbacks ⏩/🔗); the set is 23 names now — see **Icons** in the *Themes* section.

**Real two-sink crossfader** (`src/app.rs`, `src/audio/transition.rs`):
- **Two sinks, one mixer**: `self.sink` plays the current track full-length
  (never truncated); the arm creates a second `Player::connect_new(self.mixer)`
  (`xf_sink`) holding the buffered incoming track. Both play simultaneously;
  rodio mixes them. Each track is heard exactly once — the old three-piece
  queue (`A_body` + `mix(A_tail,B_head)` + `B_body`) is deleted, which also
  killed B's repeated tail (B_tail re-read at the end of B_body) and the
  multi-second UI freeze from eager `skip_duration()`.
- **Arm** (`advance()` step 2, decided by `transition::arm_plan`): within
  `crossfade_secs` of the outgoing track's end (or `PREROLL_SECS` with gapless),
  `peek_next_index()` is consulted (and the pick **committed** once, on success)
  and the incoming source is built
  synchronously (buffered decode — header-only, ms). `xf_out_total` = outgoing
  duration is captured, then `current_index`/`current_path`/`total_duration` flip
  to the incoming track so Now Playing and the seek bar already show it.
  `playback_position()`/`playback_position_secs()` prefer `xf_sink` while present.
  Missing next file → skip the arm; natural advance fails it gracefully via
  `play_now`.
  **Short-incoming guard**: a track whose tagged duration is shorter than the
  hold/fade window would drain muted while "playing" then be promoted empty
  (silent skip). `arm_plan` reads `tag_cache` and bails when `duration < hold`
  (gapless hold = remaining time / crossfade hold = `crossfade_secs`) — such
  tracks play via natural advance with a gap instead. Untagged tracks are
  allowed through.
- **Settle** (`advance()` step 1): the fade progression is
  `transition::xf_gains(remaining, crossfade, crossfade_secs)` — pure, and the
  other half of the same split as `arm_plan`. `remaining` comes from
  `sink.get_pos()` vs `xf_out_total` (pause/seek-safe, no wall clock), and the
  two gains set `sink`/`xf_sink` volumes each frame (equal-power, no midpoint
  dip). **Gapless returns `(1.0, 0.0)` unconditionally**, so the caller's
  per-frame block is three lines with no branch: the xf sits at volume 0 until
  the swap — zero gap. `xf_gains` deliberately does *not* repeat `p`'s clamp;
  `fade_gains` does it, and repeating it would be dead code. It *does* guard
  `crossfade_secs == 0` (the ☰ slider's floor): the division is skipped and `p`
  pinned to 1, because 0/0 is NaN and `clamp` propagates NaN into both sinks'
  volume — pinned by `xf_gains_is_finite_for_a_zero_length_crossfade`. When the
  outgoing sink empties → `finish_xf()`: stop the outgoing sink, promote
  `xf_sink` to `self.sink`, restore full volume, zero `position_offset`.
- **Seek-first builders**: `transition::seek_or_skip()` tries `try_seek()`
  (FLAC binary search ~µs, WAV/OGG/M4A fast) before falling back to
  `skip_duration()` — turns the freeze into an instant seek for seekable formats.
- **Cancellation** (`cancel_xf()`): stops + drops `xf_sink`, restores main volume. Called from `start_track`, `seek`,
  `stop`, `remove_track`, `move_track` and `playlist_reordered` (seek/stop/remove/move/reorder/start
  invalidation sites). `pause`/`play` drive both sinks.
  - **Known adjacent defect, not fixed:** `cancel_xf` leaves `current_path`/`current_index` describing the
    **incoming** track, which the arm already flipped to, while the **outgoing** one is what `self.sink` is
    actually playing. So a cancel leaves the metadata naming a track that is not playing. Pre-existing and
    hit today by `remove_track`/`move_track`; the playlist ops inherit it identically rather than adding to
    it. A correct fix needs the outgoing track's **id** — the app saves only its *duration* (`xf_out_total`),
    so it would take a `sink_track: Option<PathBuf>` field. Out of scope here; do not "fix" it by editing
    `cancel_xf` alone.

**Tests added**:
- `tests/balance_tests.rs` — 8 tests: curve, mono/stereo routing, bit-transparent passthrough, live change mid-stream, seek clears half-frame.
- `tests/gapless_crossfade.rs` — 28 tests in four groups. `fade_gains`: endpoints, midpoint ≈ 0.707, constant-power a²+b²=1, monotonicity, clamping. `xf_gains`: both window edges, midpoint equal-power, overshoot past the window, monotonic across 300 points with a documented `1e-6` tolerance, the gapless `(1, 0)` hold including a zero-length window, and agreement with `fade_gains`. `arm_plan`: every guard, mutation-checked. `build_gapless_next` on a real WAV: full-length drain, 0 dB/center passthrough of a mid-file sample, and no-panic on unreadable input.
  **The tolerance in `xf_gains_advances_monotonically` is not sloppiness**: `f32::FRAC_PI_2` rounds *up* (1.5707963705 vs 1.5707963268), so `fade_gains(1.0)` is `(-4.37e-8, 1.0)`, not `(0, 1)`. The outgoing sink is set to −4e-8 of full volume on the last frame before the swap — inaudible, and the sink is replaced immediately. Pinning the exact value keeps the next person from "fixing" it. It is stated in full in exactly two places — here, and the doc comment on `xf_gains_advances_monotonically` itself, which is where a reader meets the surprise. `transition.rs` compresses it to one sentence and names the test, because three copies of a numeric curiosity is two too many and none of the three is checked against the others.
- `tests/config_persistence.rs` — round-trip, defaults, JSON keys, and the `should_flush` throttle.

**Accepted edge**: duration-probe inaccuracy can make the swap (or fade
completion) land a few samples early/late → a tiny volume pop on the incoming
track; correction is a more accurate MP3 probe, not a design change. (ReplayGain
and per-track EQ are still to-do and live under *Future milestones* → **Deferred**.)

## Non-obvious machinery

- **Seek fast/slow path** (`seek` in app.rs): try `Player::try_seek()`; if it fails, reopen the file and play through with `source.skip_duration(target)`. `try_seek` reaches the decoder because `EqSource` and `TapSource` forward it; `TrackPosition` then reports the new position in-place, so the whole file-based slow path is a fallback. FLAC needs rodio ≥ 0.21: `Decoder::try_from(File)` supplies the stream `byte_len` (still true in 0.22, re-checked at the 0.22 bump) that symphonia's FLAC reader requires for its binary-search range (rodio 0.19 hardcoded it `None`, so every FLAC seek failed with `Unseekable` and fell back to decode-from-zero — no seektable helps, the range check runs first). Symphonia's FLAC binary search is ~40µs with or without a seektable, so no seektable is built anymore.
- **EQ Source wrapper** (`src/audio/eq.rs`): a custom `rodio::Source` chaining 10 biquad filters (Direct Form II transposed) in series, per-sample in `next()`, using RBJ peaking coefficients (w3.org audio-eq-cookbook) with the sample rate taken from the inner source. `refresh()` read-locks the shared gains (the GUI write-locks them) every `REFRESH_EVERY` samples and rebuilds **only the bands that changed** as fresh `Biquad`s with zeroed state — no click from stale history. `enabled=false` skips processing entirely, and 0 dB is an exact identity filter (RBJ peaking at A=1), so no bypass path is needed. Decoder outputs f32 (`rodio::Sample` is `f32` without the `64bit` feature, so the chain is f32 end to end). **`Source::channels()` and `sample_rate()` are `NonZero` in 0.22** (`ChannelCount`/`SampleRate`), so each of the three sources forwards them unchanged and unwraps the newtype once at the boundary into the `u16`/`u32` its own arithmetic uses. Because the gains are live in `Arc<RwLock<EqShared>>`, there is no sink rebuild and no audio restart. **The poll interval is the one place the two live-shared sources differ, and the difference is not tidiness.** `EqSource` may poll coarsely: it sees whole samples and has no state that spans a frame, so a gain change lands between samples and is bit-identical to a per-sample poll, only `REFRESH_EVERY` samples later (~0.7 ms at 44.1 kHz). `BalanceSource` may **not** — it emits a frame's two channels from two `next()` calls and holds the right one in `half_frame` in between, so a value that changed in between would scale the left with one gain and the right with the other. Its per-sample read is load-bearing, and `refresh` dropping `half_frame` on a change is the same fact seen from the other side. Ask which question a poll is answering before giving it an interval.
- **No lock in an audio path unwraps.** `EqShared`, the balance `Arc` and `VizBuf` are read on the audio thread 44.1k times a second, and every acquisition is `unwrap_or_else(PoisonError::into_inner)` rather than `unwrap()`. None of these guards can actually be poisoned — no panicking operation runs while one is live — so the poison flag is close to unreachable; the point is *which* way it fails if it ever is set. A `Mutex`/`RwLock` the GUI poisoned would put a panic **inside the cpal callback**, which is not a recoverable error but an abort of the whole process with no window left to close. Absorbing the poison degrades to "keep playing with possibly-stale settings", which is the same failure a dropped frame costs.
- **Visualization tap source** (`src/audio/viz.rs`): `TapSource` wraps `EqSource` (post-EQ) and mono-downmixes into a capped ring buffer (`VizBuf`, 16384 samples ≈ 372 ms — the size is load-bearing for the read cursor, see **Visualizer** → *the tap delivers audio in bursts*). **The buffer also carries the source's sample rate**, written by `TapSource::new` and read by `compute_bands` for the band→bin mapping: the mapping is 20 Hz..Nyquist *log*-spaced, so pinning 44.1 kHz put every band edge ~9% off on a 48 kHz file. A source is the only thing that knows the rate, which is why it rides with the samples rather than being passed in. During a crossfade the rate flips to the incoming track when the arm builds its tap — a mixed-rate overlap is approximate either way, and this is closer than a fixed assumption. The GUI reads a **cursor-advanced** window each frame rather than the raw tail — `read_window(n, dt)` is what turns one audio burst into many small steps, and the reason is under **Visualizer** → *the tap delivers audio in bursts* — then runs a 1024-point radix-2 FFT with Hann window, maps to 32 log-spaced bands, dB-normalizes, and applies per-bin attack/release smoothing. Both `start_track` and `seek` append the tap; `start_track`/`stop()` clear the buffer so stopped playback shows flat idle. Pure logic — no audio device needed for tests.
- **Slider pinning + position offset**: the slow-path seek rebuilds the sink with a `skip_duration(target)` source; rodio's `get_pos()` counts only post-skip samples, so the fresh sink under-reports by exactly the skip amount. `position_offset: Duration` compensates, and **every read goes through `effective_pos(sink_pos, offset)`** — a one-line free function in `app.rs`, `saturating_add` because the two inputs are independent (real playback time vs. a *previous* skip) and a bad pair must not panic in the audio path. It is set to the seek target on slow seek, zeroed after a fast `try_seek` (which already reports the new position), cleared on load/stop. Three call sites (`advance`'s settle block, its arm input, and `playback_position_secs`), which is why they share a name: the failure is silent, and three copies of one addition is three chances to drift. The one site that must *not* offset is `playback_position_secs`'s xf branch — the xf sink was built by seeking the incoming track, so its position is already absolute. **This is the only part of the seek path with no integration coverage, and it can't get any**: `try_seek` succeeds for every format a test can cheaply produce, so the `skip_duration` fallback never runs. Hence the free function and `tests/seek_position.rs`. The time label shows the new position immediately and the slider pin (`seek_target`, held until `get_pos` catches up) releases within a frame. The bar's resting state follows `playback_position()` every frame — the `seek_target` branch only holds during catch-up, and the plain-else branch tracks playback when no seek is in flight, so a track change (`start_track` clears `seek_target`) resets the bar to 0:00.
- **Sink replacement on load/seek**: replacing the sink (via `Player::connect_new(&self.mixer)` — one shared mixer, old sink's Drop stops its queue) drops the old decoder and releases the file handle.
- **System font fallback** (`theme::install_fallback_fonts` + `SYSTEM_FONT_CANDIDATES`): egui's bundled fonts (Ubuntu-Light subset etc.) lack some Unicode — e.g. U+2010 HYPHEN in "Ne‐Yo" tofu'd because the subset's punctuation coverage starts at U+2013. At startup the first existing system font (DejaVu/Liberation/FreeSans/Arial/Segoe paths; `.ttc` collections skipped via a magic-byte check) is appended last to both font families, filling only missing glyphs. App-wide, not per-theme.
- **Per-frame UI state in egui Memory**: `TPlayApp` holds no per-frame UI state — no widget values, no layout, no dock tree. The seek slider position (`tplay.seek` in now_playing.rs), the drag-and-drop state (`tplay.drag_from` / `tplay.drag_hover` in playlist.rs), the library init flag and search query (`tplay.library.init` in `library/mod.rs` / `tplay.library.query` in `library/listing.rs`) are stored via `ui.ctx().memory_mut` so they survive across frames and between panes.
- **`played` changes only on a play, a playlist edit, or a stop — never on a frame.** `played: Vec<usize>` is the history of indices played in this shuffle cycle: `next_track_index` picks random from the unplayed pool, `prev_track_index` pops from it, clicking a track directly resets it (`played.clear()`), and reordering/deleting calls `reset_shuffle()`. The picking logic is split in two, and the split is the invariant:
  - **`peek_next_index(&self) -> Option<(usize, u64)>`** — pure. `&self` plus an rng drawn from a *scratch copy* means it **cannot** write `played` or consume entropy; the type signature enforces it, not a convention. Returns the candidate together with the post-draw rng so a commit installs exactly the draw that was peeked.
  - **`commit_next_index(idx, rng)`** — the only writer of `played`, called once per track that actually starts playing. On an exhausted pool with repeat it clears the history first (spelled as the same "every index played" test the peek used, not a length compare).
  - **`next_track_index()`** — the two composed, for every caller that is genuinely about to start a track (`next`/`prev`/`play_track`/natural advance/the arm).

  `prev` is split the same way — **`peek_prev_index` + `commit_prev`** — and for the same reason: `has_prev_track` asks it every frame to decide whether to light the button, so it must be pure. With more than one history entry the target is the **second-to-last**, because stepping back pops the track being left; that pop is `commit_prev`'s, gated on `len() > 1` so a single-entry history loops without consuming itself.

  **`has_next_track` / `has_prev_track` are one-liners over the peek functions.** They used to be independent re-implementations of both traversals' branches, and the copies had already drifted: the prev one read `played.len() > 1 || repeat`, which is `true` for an *empty* history — reachable by clicking any playlist row with shuffle on, since `play_track` resets the history and `start` never pushes to it. The transport button lit and `prev_track_index()` returned `None`, so it did nothing. Deriving both fixed it; the only behaviour change in the whole refactor is that state, where prev now reports unavailable. `can_play()` is deliberately *not* derived this way — it asks a different question (loaded, or a non-empty playlist, minus an in-flight spool) and every line of it earns itself.

  **Why it is split:** the gapless/crossfade arm re-evaluates itself on *every frame* until it resolves, so anything it calls runs 60×/second. It originally called the picking function, which appended to `played` every time — the shuffle order was rewritten by deliberation rather than by playback, and `prev_track_index` (which pops that history) walked to tracks that never played. Worse, the mode check had moved into `arm_plan`, so with both modes *off* the block still ran and did it for free. The arm now peeks, and commits only when the arm actually lands. Two consequences worth knowing: a peek is idempotent, so the candidate cannot flicker between frames; and a **skipped** arm (nothing to pre-buffer, too short, build failed) commits *nothing*, so natural advance picks fresh at the track end instead of inheriting a stale entry. Pinned by `playlist_shuffle.rs` (`peeking_repeatedly_changes_neither_history_nor_rng`, `an_uncommitted_peek_leaves_the_order_alone`, `an_armed_track_commits_exactly_one_entry`, `history_length_tracks_plays_not_frames`, `repeat_restarts_the_cycle_on_commit_not_on_peek`).
  - **Those five pin a *mirror*, and for a long time that was the only thing that existed** — which is why the real `peek_next_index` could be wrong with the suite green. Found while rewriting the unplayed pool: inverting the membership set and shifting the mark by one both left all seventeen mirror tests passing, because none of them calls the function. `a_shuffle_cycle_through_the_app_is_a_permutation` (in `playlist_edit.rs`) now drives the real thing through `next_track` and fails on both, because a track repeated means a live one was wrongly marked played and a track skipped means one was wrongly left in the pool — neither of which shows up as a wrong *order*, which is all a mirror can compare. **Prefer extracting the logic over mirroring it; where a mirror is unavoidable, say so and also drive the original.**
  - The pool is built with **one membership pass** (`Vec<bool>` sized to the list), not a `played.contains` scan per candidate: `peek_next_index` runs every frame from the transport's `has_next_track` and again through the arm, and `len` linear scans of a `Vec` is quadratic in exactly the mode whose purpose is playing long lists. The mark is written through `get_mut` for the same reason `move_track` is bounds-guarded — a stale entry is skipped rather than indexing past the end.
- **Dock state in egui Memory**: `DockState<Pane>` lives in `ctx.data()` under `tplay.dock_state`. Pure UI state — not in `TPlayApp`, not in the `TPlay` shell either, since `ctx.data()` already scopes it to the context. Layout persists to disk each frame.
- **Shared tag scan**: one cache (`tag_cache`) serves every pane, fed by two transports, and **`tracks::TagReader` owns the split** so the app holds no mpsc plumbing and no `tag_scan_rx` field. `TPlayApp::ensure_tags(paths) -> bool` forwards to `TagReader::request(cache, network, paths)` and returns whether a scan started, so the caller can request a repaint (the app has no `Context`), `TagReader::request` skips cached tracks and hands the local half to a background `scan_files` thread (replacing any in-flight receiver — per-track cache means a dropped scan just restarts next request) and the remote half to `Network::fetch_tags` (see **Remote tags**). Results drain per frame via `TagReader::drain_into` (local, including the mpsc `Empty`/`Disconnected` branches that clear "Scanning…") and `TagReader::absorb` from the `Event::Tagged` arm of `update()` (remote, including `MAX_TAG_FAILURES_LOGGED` which moved with it). Triggers: library `navigate_to` and the share browser, playlist `add_files`, `load_playlist_from`. `drain_tag_scan()` returns the matching bool for the same reason. `start_track` reads the playing track's tags inline (one file) so Now Playing shows title · artist · album immediately. `library_scanning()` recomputes as "any current-folder file missing from the cache" — a **local** question by construction, since the entries only ever come from `navigate_to` over a `dir.is_dir()`-checked dir and an `smb://` URI never passes that; the share browser computes the same thing over its own entries.
- **SMB worker** (`network::spawn_worker`, spawned by `Network::new`): a single `std::thread` owns a tokio current-thread runtime and processes `SmbCmd`s sequentially (`ListShares`/`ListDir`/`Spool`/`Save`/`Tags` — paced by user clicks, spool is the one long op). Replies come back over a std mpsc drained every frame by `Network::drain` (same pattern as `drain_tag_scan`; `TPlayApp::update` returns true — so the shell repaints — while `busy()` or playing). Each command carries its own `SmbCreds` snapshot (saved username + session password) — passwords exist only inside the command and are dropped after use. Stale replies are dropped by the `host`/`uri` match against the current browse/pending state. Sequential processing means a `Save` queues behind an in-flight track spool — fine for a few KB of JSON, but a large download makes Save feel slow. A `Tags` batch is likewise a long pole, and now a much heavier one: browsing into a 300-file directory queues one command that **downloads 300 whole files**, and browse clicks wait behind all of it. That is the price of remote rows matching local ones (see **Remote tags**); the share browser shows a live count so the wait is legible, and a revisit is instant because the files are already cached.
- **Four in-flight slots, one per concern** (`network.rs`): `pending` (playback spool, read by Now Playing for "Loading from server…" and by `advance()`'s cascade guard), `fetch_req` (a remote `.tplay` download), `saving` (a share write — **a count, not a bool**, and that is load-bearing: saving an already-tracked playlist needs no dialog, so two clicks queue two writes, and a bool cleared by the first reply left `busy()` false with the second reply undrained), `tagging` (the set of URIs with a tag request in flight — see **Remote tags** for why it is not the same map as the failure counts). `drain` returns the **first actionable** event and leaves the rest queued, so `update()` drains in a `while let` loop — a save reply must not be stranded behind an unrelated one, and the loop can't spin (each `Some` consumed a reply). All four feed `busy()`, which is one of the terms in the `bool` `update()` returns for the shell to turn into `request_repaint`: anything in flight that `busy()` doesn't know about sits undrained until some unrelated repaint happens. That is the whole reason a slot may not under-count.
- **Two maps, no shared insert path** (`library_db.rs`). The tag cache and the per-track play history are separate `HashMap`s inside `TrackDb`, and that is not a data-modelling preference — it is what makes "a re-scan cannot erase a play count" a **type error** instead of a rule. The background scan fills the cache through `db.cache_mut()`, which is the same `&mut TagCache` it always had, and `TagReader`'s two write sites (`drain_into`, `absorb`) are **unchanged**: neither one ever holds a `&mut TrackDb`, so neither can see a play count at all. The alternative — one row type with a `record()` that copies the mutable fields back — puts a 3-line merge in the path of every future writer, and a writer that forgets it costs a user their history with no error anywhere. The stamp has the same shape: `first_seen` is written by **`TrackDb::persist` alone**, because that is the one place no insert can bypass, and "first seen" only means something once it has been written down. Both halves are mutation-checked in `library_db.rs` — turning the file struct's `BTreeMap` back into a `HashMap` fails `the_file_is_written_in_key_order`, and making the stamp overwrite instead of fill fails three others. **What the file says and what we know are kept apart per field, not by rule**: a rating is a Popularimeter in the file, so it is re-readable and portable; a play count is not a tag key any player stores, so raising one in the file would mean a disk write on every play — which fails outright on a read-only mount and is meaningless against a spool-cache copy of a track on a server.
- **The tag cache holds `TrackInfo`, not `Option<TrackInfo>`.** "Checked, no tags" is therefore recorded as an **empty** `TrackInfo`, which is what `scan_files` already stores for an untagged local file. Every reader treats that identically to no entry — `title_or_stem` falls back to the stem on an empty title, and the search haystack and Now Playing labels see empty strings — so nothing needs to distinguish the two. The one thing that *does* need the empty entry is the "don't re-request" rule, and it applies to **failures** too: `scan_files` used to skip a file lofty could not parse, which meant it never entered the cache and `library_scanning()` ("missing from the cache") held `Scanning…` on screen for the rest of the session. It now sends an empty `TrackInfo` for those as well, so both sides follow one rule — pinned by `the_scan_reports_a_result_for_every_file_asked_about`. The share browser additionally shows "Reading tags… (N unavailable)" once in-flight work hits zero, so a track that gave up after its retries cannot pin a count on screen forever.
- **Appwide settings**: one `~/.config/tplay/config.json` holds everything — theme, EQ (enabled + gains), shuffle/repeat, visualizer view (`viz_view`), volume, last loaded playlist, saved SMB servers (`servers`), and the library state (favorites, last dir, show hidden). Loaded once, in `main.rs`, and handed to `TPlayApp::new(&config, db, mixer)` (which also needs it, for every persisted field). Shuffle/repeat are global playback modes — loading a playlist never touches them. Volume is applied to the sink at startup. The last loaded `.tplay` (`last_playlist`) is re-loaded on startup (Library + tag scan + tracked file all restored), so Save Playlist keeps overwriting the same file across sessions.
  - **Writes are decided by content, not by a flag.** `TPlayApp::update` calls `flush_config(now, closing, theme_id)` once per frame (the shell reads the clock, the close flag and the theme id off the `Context`). The app holds a `config::Persisted` — the last content written and when — seeded in `new(&config, db, mixer)` from the config and database it was handed, so a clean start writes nothing. The flush is **two questions, and the order is the point**: `Persisted::due(now, closing)` first, which is *whether it is worth serializing at all*, and only then the content compare. `snapshot(theme_id)` lists every `Config` field explicitly (no `..Default::default()`, so a new field is a compile error there rather than a silent reset) and the answer decides whether that string differs from the last one written.
    - **`due` comes first because the point of the debounce is to avoid the work.** Inside the window the answer to `wants_write` cannot be "yes" anyway, so serializing to find out is pure waste — and the waste is not equal across the two files. `config.json` is ~500 bytes; a `library.json` is the *whole tag cache*, so the same line becomes megabytes a second and grows with the library. That is `flush_db`'s reason for existing as a second call rather than a second mode, and why `TrackDb::snapshot` borrows (`DbFileRef`) rather than owning. `closing` skips the debounce, which is what buys back a change made inside the window.
    - Why not a dirty flag: it was a **manual obligation with 21 call sites**, and a missed one silently lost a setting — forget `mark_config_dirty()` in the server-CRUD path and the NAS server vanishes on restart. The compare cannot be forgotten, because it doesn't ask anyone. It is also strictly more correct: the widgets fire `resp.changed()` on **every frame of a drag**, so the EQ pane's 10 sliders plus volume and balance were serializing and `fs::write`-ing ~60×/sec. A drag that changes a value and changes it back now writes *nothing at all*.
    - **This is the shape `gui/coordinator.rs` already used for `dock_layout.json`** (`DOCK_SAVED_JSON`); config.json simply had never got it. Same `closing` branch, same trade: at most one debounce window (0.5s) of settings is lost on a hard kill, which the flush on `close_requested` buys back.
    - `note_written` is called **before** the file is written, not after. A write that fails is then not retried every frame for the rest of the session — the alternative is a disk that is full or a mount that went read-only turning into a 60Hz retry loop. For `flush_db` it also matters that the string compared against next frame is the one that *reached* the file: `persist` stamps `first_seen`, so comparing a pre-stamp snapshot would make every frame after a new track look changed.
    - Two accepted consequences: **one write at startup** if `config.json` isn't byte-identical to canonical `to_string_pretty` output, and — the same reason for the database — the fact that a file whose serialization is *order-dependent* would defeat the compare entirely. That write normalizes the file and persists the clamp of any hand-edited out-of-range value, not data loss, since unknown keys already died on the first real change. The mechanism is only sound if equal content serializes equally, which `config_persistence.rs` pins (a `HashMap`/`HashSet` field would make every frame look changed) and which `library_db.rs` pins again for the same reason.
  - **The four state groups.** `TPlayApp` used to hold 40 flat fields, four groups of which had a natural owner. Each is now one field, exposed as one accessor pair rather than a per-value delegate:
    | group | owner | accessor | what moved out of `app.rs` |
    |---|---|---|---|
    | eq gains/enabled/presets | `audio::eq::EqSettings` | `eq()` / `eq_mut()` | the `Arc<RwLock<EqShared>>` field, the +/-12 dB clamp, the preset apply |
    | theme + list + icons | `gui::theme::ThemeState` | **not app state** — owned by `main.rs`'s `TPlay` shell | three fields, the `egui::Context` needed to re-decode icons, and every pane's palette/metadata-font read |
    | six playback settings | `config::Prefs` | `prefs()` / `prefs_mut()` | twelve setters' clamping (and their change-detection, now unused) |
    | library dir/rows/sort/favorites/hidden | `library::LibraryState` | `library()` / `library_mut()` | six fields; see below |
    | SMB servers/creds/spool/browse | `network::Network` | `network()` / `network_mut()` | already the case; the three one-line forwards over it are gone |

    **32 forwards died with this** (12 setters, 20 getters, plus `quick_folders` / `set_network_password` / `fetch_remote_playlist`), taking `app.rs` from 82 `pub fn` to 58. What is left is app-only state, cross-owner effects, and these 10 accessors. The one-line forwards were not an abstraction: each named a method the app did not own, so the call site read as `app` state when it was really `Prefs`/`EqSettings`/`LibraryState`/`Network` state — and the asymmetry was the tell. `app.library().favorites()` sitting next to `app.toggle_favorite(dir)` was unreachable *because* the setter had to raise a flag; with the content compare, it is `app.library_mut().toggle_favorite(dir)` and the getter is the same object.

    `balance` and `eq` stay `Arc`-backed because a source reads them per frame; the owners hand out a **cloned** handle (`balance_shared()` / `shared()`), never a borrow, since the source outlives it.
  - **`LibraryState` splits state from effect.** `navigate_to` used to list the folder *and* kick off a tag scan, which welded the Library's state to the app's scanning machinery — so it could not be exercised in a test at all. `LibraryState::open(dir, tags)` now lists, sorts, and **returns the paths that need scanning**; `TPlayApp::navigate_to` keeps the `ensure_tags` call, because the tag cache and the `TagReader` are shared with the Playlist and Now Playing panes and so are not the Library's to own. `library::TagCache` (an alias for `HashMap<PathBuf, TrackInfo>`) exists because that type is in four signatures now and the key is a *track id* — an `smb://` URI in a `PathBuf` for a remote one.
  - **Config JSON structure**: see **Config & data files** — the block there is the complete one.
- **Confirm dialogs**: `gui/dialogs.rs` holds the app's only two modals, both in-app `egui::Modal`s — **no native OS file or message browser anywhere** (`rfd` is gone; don't re-add it). A call site arms one with `dialogs::ask(ctx, ConfirmAction::…, title, desc)` and the coordinator draws it at the end of the frame, so a pane or the ☰ menu can raise it. Arms: per-track ✕ removal, Create Playlist, loading a playlist over a dirty one, deleting a saved layout. The action is an **enum, not a closure** — a closure cannot be stored in egui memory — so `run` is the one dispatch point, and it is the one place a stale value can arrive: an armed playlist index can outlive its row (an in-flight remote playlist can replace the list), which is why that arm re-checks the index before `remove_track` (which would panic). "Nothing at risk" (a clean playlist) skips the modal and acts directly — the old `at_risk` flag is now a call-site `if`.
- **XorShift64 RNG** (`playlist.rs`): inline 64-bit XorShift (`state ^= state << 13; state ^= state >> 7; state ^= state << 17`) replaces `fastrand`. Used for shuffle track selection, the opening draw in `play_first_track`, and `shuffle_tracks`. Fixed seed `0xC0FFEE` — and it has to be non-zero, because 0 is a fixed point of the recurrence (the algorithm's known weakness) and would make every draw 0. It moved out of `app.rs` with the rest of the playlist's pure logic, because every draw it serves is a playlist shuffle.

## Test conventions

- **All tests live in `tests/`** — no `#[cfg(test)]` modules in src, and `tests/no_inline_tests.rs` fails the build if one appears (it walks `src/`, skipping comment lines so a doc comment may still *mention* `#[test]`). The reason is not tidiness: cargo compiles an inline module into **both** the `lib` and the `main` unit-test binaries, so `src/audio/viz.rs`'s 8 tests ran **twice** under two unnameable targets and could not be run or filtered as a suite. Moving them to `tests/viz_tests.rs` made them run once, as a target you can name. Cargo auto-discovers each `tests/<suite>.rs` as its own binary, so every suite runs exactly once (`tests/main.rs` was removed — it re-declared the suites and doubled every run). A private helper is reachable from a suite by making it `pub` — the only reason `audio::viz::fft_magnitude` is public.
- `tests/common.rs` helpers: `temp_dir()`, `test_dir(name)`, `write_wav(path)` (1s 8kHz mono PCM), `write_aiff(path, title, artist)`, `write_minimal_flac(path)` (headers only), `write_tagged_mp3(path, title, artist, album)` (a real ~125 KB MP3 with real ID3v2 tags), `assert_duration_approx`, `lay_out::<T>(tree)` (the egui_dock finite-viewport fix, shared by `dock_layout.rs` and `layout_save_load.rs`), and the `TestApp` harness — `new`, `pump`, `pump_until_empty`, `pump_during(f)` (the one that moves the `MixerSource` into a scoped thread so the mixer runs while `f` blocks, which is how the blocking `try_seek` is serviced in a test).
- **`tests/fixtures/` — eight committed real audio files, one per format, and the only fixtures that are not hand-built.** `tests/common.rs` builds its own because nothing in the dependency tree can *encode* audio, which is a fact about the crates and not a reason to ship a synthetic file when a real one exists: a 1 s tone says a decoder opened the file, and nothing about where that format keeps its tag block or whether its declared duration survives a round trip. All eight are one 12.27 s / 44.1 kHz recording in eight containers (CC0, from `audiojs/audio-lena`, which is freesound #246148 by *heshamwhite* — `tests/fixtures/README.md` and `CREDITS` have the provenance), so a duration assertion means the same thing in each and the four tagged formats put their tags in **four different containers' worth of places** — a native `VORBIS_COMMENT` block, a Vorbis comment packet, ID3v2, and a `LIST`/`INFO` chunk. They close three real gaps: **FLAC had no audio at all** (`write_minimal_flac` is headers only) and **OGG and M4A had no fixture whatsoever**. `common.rs` is unchanged and still load-bearing — `write_aiff` in particular must stay hand-built, because `symphonia_misreads_the_aiff_sample_rate` is a tripwire whose premise is a provably correct 8000 Hz rate. **Do not regenerate them:** `ffmpeg` is not a build dependency and the suite is hermetic. 13 of the upstream project's 21 files are deliberately absent (10 MB with no demuxer in this stack) — add one only alongside a test that needs it.
- Test isolation: each test makes its own temp dir under `/tmp/tplay-test-<pid>/<name>/` and removes it. `audio_fixtures.rs` is the one suite that reads a path it did not create (`CARGO_MANIFEST_DIR`-relative, since cargo promises no working directory) and so writes nothing.
- Run: `cargo test` (all suites, once each).

### Audio formats this stack cannot play

Not a milestone — a list of formats `AUDIO_EXTENSIONS` deliberately leaves out,
each with the test that says when to add it back. The playlist half of interop
(`.m3u` / `.m3u8` / `.pls`) **shipped** and is under **Playlist** → **One
playlist file format**; what is left is the audio half, and the reason for each
gap is a measurement rather than a preference.

- **AIFF** — symphonia 0.5.5 *has* an AIFF demuxer and lofty reads its tags, so
  it looks free, but the sample rate comes from the `extended` 0.1.0 crate,
  whose `to_f64` normalizes the 80-bit float as if its top bit were not the
  implicit leading one. It reads **8000 Hz as 3904**, so such a track plays two
  octaves up and ~4x fast, and `total_duration` (4x short) would feed the seek bar
  and the crossfade math. `symphonia_misreads_the_aiff_sample_rate`
  (`library_tests.rs`) is the tripwire: when it fails, the bug is fixed — add
  `aif`/`aiff` to `AUDIO_EXTENSIONS` and delete the test.
  **The bug is a property of that value, not of the container, and this used to be
  documented wrong.** It was also claimed to turn 44100 Hz into 11332; a committed
  real 44.1 kHz AIFF (`tests/fixtures/lena.aiff`) decodes at **44100**, correct,
  with a correct duration — `a_correctly_encoded_44100_aiff_is_not_rate_mangled`
  in `audio_fixtures.rs` pins that. So re-enabling AIFF is a per-rate check, not a
  blanket undo, and 44.1 kHz is not among the broken ones.
- **Opus** — symphonia 0.5.5 has no Opus codec crate at all (not in
  `all-codecs`), only the Ogg container, so `.opus` is not decodable today. This
  is the one of the three that `audio_fixtures.rs` verifies directly, and the
  error is rodio's own *"The format of the data has not been recognized."* — a
  container symphonia cannot even identify, which is what a missing codec looks
  like from the outside. (0.21 spelled that message "Unrecognized format"; the
  test tracks the text, so a renames-only change is cosmetic and a decode error
  of a different kind is a real regression.) **This line was wrong about the
  upgrade path and has been measured:** it used to say "wants rodio 0.22 /
  symphonia 0.6", but rodio 0.22.2 still depends on `symphonia ^0.5.5` — the
  bump is now done and Opus is exactly as unreachable as before. It needs rodio
  to move to symphonia 0.6, which is upstream, not a choice here.
- **WMA, APE, WavPack** — no upstream support; each would be a new dependency,
  and each has to justify itself per the deps table.
- **MOD/S3M/XM/IT, MIDI** — the Nullsoft hallmark. Needs a decoder dependency;
  out of scope while the dependency rule stands.
- **Raw `.aac`** — **this one was documented wrong too, and it does decode.**
  symphonia 0.5.5 parses ADTS fine; `raw_aac_decodes_but_its_lofty_duration_is_an_estimate`
  (`audio_fixtures.rs`) opens a real ADTS file and measures it. What actually
  disqualifies it is the *other* duration reader: ADTS carries no length, so
  lofty *estimates* one from the bitrate and lands ~0.5 s long (12.808 s against
  the decoder's 12.330 s), and the Library's Duration column reads lofty — so the
  row would display a wrong length while playing correctly. The right test is
  `the_decoder_and_the_tag_reader_agree_on_every_duration`, which every format in
  `AUDIO_EXTENSIONS` passes and `.aac` does not. Add `aac` when that passes.

- **ReplayGain / loudness normalization** — read `REPLAYGAIN_TRACK_GAIN` (lofty
  exposes it) and apply it as a per-track volume offset at `start_track` time, or
  as a pre-scan loudness pass. **Nothing is stored or read today**: `TrackInfo`
  has no gain field, so a claim elsewhere that "the storage half is free" was
  wrong — adding the field before there is a reader is a field nothing writes.
  When it lands it is cheap, because the field rides `TrackInfo` and
  `library.json` carries it, and a gain is read where `duration` and `rating`
  are: in `read_info`. Speculative until someone asks.
- **Per-track EQ** — conflicts with the single live `EqShared` source of truth
  (`audio/eq.rs`) and the "EQ settings are live" design; it would need a per-track
  settings map consulted at `start_track`. Not recommended without a product
  reason.
